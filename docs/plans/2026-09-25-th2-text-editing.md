Decisions:

- text mode uses the existing `TextField` undo history; each successful apply becomes **one canvas undo step**, regardless of how many lines changed (§3.5, §4.6);
- **inside text mode**, undo and redo work as in the `thconfig`/`.th` editor, through the `TextField`'s own history (§3.5);
- redo is **`Ctrl+Shift+Z` everywhere**. The canvas no longer uses `Ctrl+Y`, and the text editor accepts both Ctrl and Cmd. This change was made on its own, ahead of this plan (§2.7);
- text that doesn't parse is **never saved** (§3.6);
- the first apply of a broken file is a **new baseline that can't be undone**, and the fixed file stays unsaved until saved (§3.7, §4.7);
- text the parser rewrites or drops is **accepted as the parser reads it**, and each such line gets an information marker before the apply (§4.12);
- a selected line point **round-trips** between the two views (§3.2, §3.3);
- the mode toggle uses **F2** instead of `Ctrl+E` (§3.1);
- the editor buffer holds **each line's real line ending**, and an apply keeps it: unedited and edited lines keep their original ending, pasted lines keep the ending they were pasted with, and lines typed with Enter always get the file's default line ending (`TH2File.lineEnding`), regardless of the current line's ending, so a save changes only the lines the user edited (§4.2, §4.9);
- text mode supports `\n` and `\r\n` line endings. A file or editor buffer containing a lone `\r`, typed or pasted, is rejected before text-mode entry or apply, respectively, because the TH2 parser does not split there (§4.2);
- an element-tree edit made while the tab is in text mode **applies the text first**, and is cancelled if the text doesn't parse (§3.8, §4.13).

## 1. Overview and Objectives

Issue #38 asks for a quicker way to enter and review element options than clicking through one option dialog at a time. It points to XTherion, where options are typed as text. This plan's answer is a **text mode for `.th2` tabs**. The same tab switches between the graphical canvas and a syntax-highlighted text view of the whole file. The user can type or change any command, option or coordinate, see every option of every element at once, and then return to the canvas.

The two views are **synchronized at each switch**, not while typing:

- **Graphical → text:** the text is generated from the current model, and is exactly what Save would write. If elements are selected, the text scrolls to the **first selected element in file order** (the one nearest the top of the file), and the cursor is placed on it. A selected line point counts as an element here.
- **Text → graphical:** if the text changed, the final valid text is applied to the model as **one undoable edit**. Clearly matched unchanged elements keep their MPIDs (§4.7). The element on the cursor's line is then **selected on the canvas**, and its scrap becomes the active scrap. If the cursor is on a line point, the canvas opens in _Line edit_ mode with that point selected.

### Key objectives

1. **Text mode per `.th2` tab.** A _Text_ button on the canvas, a _Canvas_ button in the text view and `F2` switch the active tab between canvas and text. Each tab remembers its own mode.
2. **Highlighting.** TH2 commands, options, numbers, strings, comments, multiline `comment … endcomment` blocks and `##XTHERION##`/`##MAPIAH##` settings are colored. `scrap`, `line`, `area` and `comment` blocks can be folded.
3. **Lossless generation.** The text shown on entering text mode is exactly the output of the save path (`TH2FileWriter` with `includeEmptyLines: true, useOriginalRepresentation: true`). Unchanged lines keep their original formatting. Typed text is kept as the parser reads it. Where the parser rewrites or drops a line, the user is told before the apply (§4.12).
4. **Graphical → text selection.** The first selected element or line point in file order decides the scroll position and the cursor line.
5. **Text → graphical selection.** The element owning the cursor's line is selected, as if clicked in the element tree. A line point opens _Line edit_ mode with that point selected.
6. **Undo in both views.** In text mode, `Ctrl+Z`/`Ctrl+Shift+Z` use the same `TextField` history as the `thconfig`/`.th` editor. Applying the final text creates one command on the canvas undo stack (§3.5, §4.6).
7. **Safe apply.** Text that doesn't parse cleanly is never applied and never saved. The tab stays in text mode, and each problem is marked at its line.
8. **Stable identity.** An apply keeps the MPIDs of elements that can be matched unambiguously (§4.7), including a scrap or line whose header line was edited, so their selection, hidden state and the element tree's expanded scraps survive where possible.
9. **Save, dirty state and projects.** Unsaved text edits count as unsaved changes everywhere: the Save button and the overflow menu's Save item, the project tree's dirty dot, Save All (`THProjectController.saveAllModifiedFiles`, §2.5), and the rule that keeps a tab-less controller only for a saved file (§4.8).
10. **Broken files become fixable in Mapiah.** A broken file's tab can open its **raw disk content** in text mode. Once fixed, it can be applied and saved.
11. **Complete integration.** EN/PT localization, help pages, keyboard shortcuts and CHANGELOG. Controller, parser, writer, matching and widget tests. `flutter analyze` and `flutter test` stay green.

### Non-goals (this plan)

- **Live synchronization while typing.** The canvas is not updated on every keystroke. Syncing happens at the mode switch and on Save (§3.6).
- **Split view** (canvas and text side by side). The design leaves room for it (§4.1), but it is not built here.
- **An option-entry box on the canvas** (the literal proposal in #38). Text mode covers the need. A per-element text box can be a later follow-up that reuses this plan's parser and apply path.
- **Autocompletion or option suggestions.** Parser diagnostics update after an idle delay, and apply validates the final content (§4.6).
- **Per-line or per-keystroke undo on the canvas.** Each successful apply is one canvas undo step (§3.5).
- **A custom undo for the text editor.** TH2 text mode keeps the undo that `thconfig`/`.th` tabs already use (§3.5).
- **Text editing of files that are not `.th2`.** `thconfig`/`.th` files already have their own text tabs.

## 2. Grounding: Current State

### 2.1 Text editor for `thconfig`/`.th` files

- `THTextEditorWidget` (`lib/src/widgets/th_text_editor_widget.dart`, 948 lines) is a self-built editor with no code-editor dependency. It has a line-number gutter, a `TextField` with a syntax-highlighting overlay, diagnostic line markers, folding, and a find/replace bar.
- It takes a concrete `THTextEditorController` (`lib/src/controllers/th_text_editor_controller.dart`). It uses only these members: `content`, `setContent`, `isDirty`, `cursorLine`, `setCursorPosition`, `pendingScrollToLine`/`clearPendingScrollToLine`, `pendingSelectionRange`/`clearPendingSelectionRange`, `diagnostics`, `textEditorFocusNode`, `save`, `revert`, and the find members (`findQuery`, `replaceQuery`, `findCaseSensitive`, `findMatches`, `activeMatchIndex`, `isFindBarVisible`, `openFindBar`, `closeFindBar`, `findNext`, `findPrevious`, `replaceActiveMatch`, `replaceAllMatches`, `setFindQuery`, `setReplaceQuery`, `setFindCaseSensitive`).
- `THTextEditorController` is bound to `THProjectController`. It owns a project epoch/root identity, calls `registerTextContentChange` and a debounced `reparseFile`, and saves through the project. None of that applies to a `.th2` file, whose model is owned by `TH2FileEditController`.
- The widget listens to its `TextEditingController` (`_onTextEditingChanged`, `:121`, added as a listener at `:75`) and relies on the `TextField`'s built-in undo history. That history records a step after a 500 ms pause in typing. Programmatic changes (auto-indent, block indent, Replace, Replace All, Revert) go into it too. Its shortcut map binds `Ctrl+Z`/`Cmd+Z` to `UndoTextIntent` and `Ctrl+Shift+Z`/`Cmd+Shift+Z` to `RedoTextIntent`, so both modifier keys work on every platform (§2.7).
- `diagnostics` is `List<THProjectParseError>`. The widget renders them in `_buildDiagnosticBackground` (`:769-798`) and `THTextEditorDiagnosticMarkerWidget`. It keys them by line (`:775`), so only **one diagnostic per line** is drawn.
- The widget keeps the text with its line endings as they are: a CRLF `thconfig`/`.th` file is shown with its `\r\n` endings in the `TextField`. It counts lines by `\n` (gutter, `_lineColumnAt`), so a `\r\n` line is one line. It detects Enter in `_onTextEditingChanged` (`:121`) as a one-character insertion of `\n`, and adds the auto-indent right there.
- The editor's toolbar (`_buildToolbar`, `:608-647`) has a Save button and a Revert button, both enabled by `isDirty` (`:617-627`). Save calls `_handleSaveIntent` (`:313-315`), the same handler as `Ctrl+S`, which awaits `controller.save()` and ignores its result. `THTextEditorController.save()` returns `Future<THTextFileSaveResult>` (`th_text_editor_controller.dart:506`).
- `_applyPendingSelectionRange` (`:351-373`), which applies `pendingSelectionRange`, always ends with `textEditorFocusNode.requestFocus()`. `_applyPendingScrollToLine` (`:320-346`) doesn't request focus.
- Auto-indent (`_computeAutoIndent`) adds two spaces after a line that opens a block. The openers are a fixed Therion set (`_thTextEditorBlockOpeners`, `:14-20`: `survey`, `centreline`, `map`, `scrap`, `layout`).
- `tokenizeTherionText` (`lib/src/auxiliary/th_text_editor_syntax_highlighter.dart`) is a stateless, per-line lexer. Its keyword set is for `thconfig`/`.th` (`survey`, `centreline`, `map`, `scrap`, `layout`, `input`, …). It has no `point`, `line`, `area`, `endline`, `endarea`, `comment`/`endcomment`. Anything from `#` to the end of the line is a comment, so `##XTHERION##` settings would be colored as comments. It keeps no state across lines, so it can't color a multiline `comment … endcomment` block.
- `buildFoldRegions` (`lib/src/auxiliary/th_text_editor_fold_aux.dart:30-34`) folds `survey`, `centreline`, `map`, `scrap` and `layout`. `line`, `area` and `comment` are not included.

### 2.2 Tabs

- `MPGeneralController` keeps `_openFileOrder` (filenames) and chooses the controller type from the filename with `isTH2Tab(filename)` (`mp_general_controller.dart:33-34`). A `.th2` tab always maps to one `TH2FileEditController`.
- `TH2FileTabsPage._buildTabContentWidget` (`lib/src/pages/th2_file_tabs_page.dart:829-880`) returns `THTextEditorTabBodyWidget` for text tabs and `TH2FileEditBodyWidget` for `.th2` tabs. `TH2FileEditBodyWidget` shows `TH2BrokenFileBodyWidget` when `snapshot.data!.problems.isNotEmpty || controller.isBroken` (`th2_file_edit_body_widget.dart:83-84`). `snapshot.data` is the load result, which the page caches in `_fileLoads` (`th2_file_tabs_page.dart:853-871`), so its `problems` never change after the load. The body's `build` reads `isBroken` outside any `Observer`, so it doesn't rebuild when `isBroken` changes.
- The canvas body (`_buildEditor`, `th2_file_edit_body_widget.dart:113-136`) is a `Stack` of the canvas and its button groups: `TH2FileEditStateActionButtonsWidget` (undo, redo and state buttons), `TH2FileEditActionButtonsWidget` (the top-right group: add element, select, zoom, …) and `TH2FileEditStateContextFABsWidget`. They exist only while the canvas is built. Below the `FutureBuilder`, outside the canvas, the body also shows `TH2FileEditLastUsedPLAButtonsWidget` and `TH2FileEditBottomStatusBarWidget` (`:100-107`), hidden only for a broken file. A last-used chip calls `elementEditController.activatePLATypeSubtypeForNewElement`, which starts a creation mode on the canvas.
- **Tab focus.** Activating a `.th2` tab requests focus on its canvas's `th2FileFocusNode` in three places: `addFileTab` (`mp_general_controller.dart:150-153`), the active-tab setter (`:255-258`) and the page's post-frame callback (`th2_file_tabs_page.dart:127-133`). That node belongs to the canvas's `MPListenerWidget` (`mp_listener_widget.dart:49`).
- The app bar's Save/Save As buttons and `_saveActiveTab` (`:1210-1242`) branch on `isTH2Tab`, and use `TH2FileEditController.enableSaveButton` as the TH2 dirty signal. So do the overflow menu's Save item (`_buildFileMenuEntries`, `:681`) and the canvas `Ctrl+S` handler (`mp_th2_file_edit_state_key_down_mixin.dart:178-188`). That handler also runs `Ctrl+Shift+S` (Save As) behind the same `enableSaveButton` check. The canvas's `Focus` returns `KeyEventResult.ignored` for every key but the arrows (`mp_listener_widget.dart:226`), so the key also reaches the page-level shortcut (`th2_file_tabs_page.dart:1074-1083`), whose `CallbackShortcuts` wraps the whole page (`:589`, `:1121`). With unsaved changes, `Ctrl+Shift+S` on the canvas therefore runs Save As twice: once from the canvas handler and once from the page. `Ctrl+S` likewise reaches the page's `_saveActiveTab` after the canvas handler. It saves only once today because `saveTH2File()` is synchronous: by the time the page checks `enableSaveButton`, the first save has already cleared it. The app bar's Save As button (`:380-383`) and the overflow menu's Save As item (`:687-689`) are disabled for a broken file (`isBroken`).
- **Save error handling.** Only `_saveActiveTab` (`:1226-1240`, the page's `Ctrl+S`) and `THProjectController._saveTH2ProjectFile` catch an exception from `saveTH2File()` and log it. The app bar's Save button (`:370-371`) and Save As button (`:383`), the overflow menu's handler (`_handleOverflowMenuAction`, `:794-800`) and the page's `Ctrl+Shift+S` (`_saveActiveTabAs`, `:1184-1207`) call `saveTH2File()` or `saveAsTH2File()` with no `try/catch`. A synchronous throw from the Save button goes to Flutter's error handler, and a failed Save As, already asynchronous, is an unhandled future error.
- `enableSaveButton` is false for a new file (`isNewFile`), so **Save is disabled for a new file** and only Save As works. `saveTH2File()` itself doesn't check `isNewFile`: called on a new file, it would write to the placeholder name (`mpNewFilePrefix`, `NEW_TH2_FILE…`) returned by `_localFile()`.

### 2.3 TH2 parser

- `TH2FileParser.parse(filename, {fileBytes, …, forceNewController})` (`th2_file_parser.dart:2992-3071`) looks up the target controller with `mpLocator.mpGeneralController.getTH2FileEditController(filename:, forceNewController:)` and fills **that controller's** `th2File` through 21 `elementEditController.executeAddElement(...)` calls. It cannot parse into a detached `TH2File` today.
- `_splitContents` (`:3325-3440`) produces `MPParseableLine`s with a 1-based `lineNumber`. A **multi-line value** is joined into one parseable line, which keeps the number of its first line: a value inside square brackets or double quotes that continues on the next line, or a line ending with `\` (`updateContinuationDelimiter`, `_slashJoinLine`). Line breaks are found by `_findLineBreak`, which only knows `\n` and `\r\n`: a lone `\r` doesn't end a line for the parser, and line numbers count `\n`s. `_injectContents` sets `_currentLineNumber` before injecting each line (`:158`).
- Broken-file detection gives `TH2FileProblem`s, each with a `lineNumber` and `sourceLine` (`lib/src/mp_file_read_write/th2_file_problem.dart`). Some errors in `_parseErrors` (petitparser `Failure` messages) carry no line number.
- `TH2FileEditController._loadOnce` (`th2_file_edit_controller.dart:~770`) parses with `forceNewController: false` and `fileBytes: _th2File.fileBytes`. `_commitLoadResult` sets `_isBroken` when there are problems or errors.
- Parsed elements keep their source text in `originalLineInTH2File`, so writing them back with `useOriginalRepresentation: true` reproduces most of the parsed text, **but not all of it**. After injecting the lines, `parse` runs three clean-up passes (`:3049-3051`):
  - `_cleanOriginalLinesInFile` (`:3091`) clears the source text of the elements flagged at 7 call sites (`:1003`, `:1083`, `:1517`, …). Examples are a border reference whose text the grammar rewrote, a scrap with a changed option, and `subtype` on a line with fewer than 2 points. The writer then generates new text for them. No problem is reported.
  - `_linesCleanUp` (`:3127`) removes a duplicate line point that has no options, and a line left with fewer than 2 points, together with its area border reference. No problem is reported.
  - `_areasCleanUp` (`:3276`) first resolves each border reference with `_resolveBorderReference` (`:3247`). When a reference spells the invalid id of a line that Mapiah rewrote (for example `-id b@1`, stored as `b_1`), it rewrites the reference the same way and clears its source text, so the writer generates a new line for it. No problem is reported. It then reports a border reference that names no line or names a non-line (`_reportUnresolvedBorder`), which makes the file broken, and removes an area left with no borders, which isn't reported by itself.
- The writer also adds text of its own. When the file's first child isn't an `encoding` line, it writes one (`th2_file_writer.dart:51-56`). It finds that first child with `th2File.childrenMPIDs.first`, so **a file with no children makes `serialize` throw** (`StateError`). Parsing an empty text reports no problem and gives such a file. In text mode, that happens as soon as the user deletes all the text, and idle validation would throw while computing the normalized text (§4.3, §4.12).
- The writer also **rewrites image lines**. Since #46 (`bcd28f18`), `_serializeMapiahImageInsertConfig` (`th2_file_writer.dart:219-241`) writes an image whose transform is a pure translation (`MPImageInsertConfig.isXTherionRepresentable`: not SVG, scale 1 and rotation 0 within tolerance) as a `##XTHERION## xth_me_image_insert` line, even when it was read as a `##MAPIAH##` line. It builds a temporary `THXTherionImageInsertConfig` with `fromMapiahImageInsertConfig` for that write. The temporary element has no stored source text, so the line is always generated, and it reuses the original element's MPID (`th_xtherion_image_insert_config.dart:306-321`).
- The writer also **moves settings lines**. Settings (`##XTHERION##`, `##MAPIAH##`) can only appear at file level: the grammar accepts them only among the top-level commands (`th2_grammar.dart:35`), not inside a scrap (`:40-41`), where such a line is read as a comment. The parser adds each setting at the end of the file's children, in text order (`th2_file_parser.dart:567`, `:633`). The writer writes all of them together at the position of the first one, and the others write nothing (`th2_file_writer.dart:87-111`). When every setting is new, the group goes right after the `encoding` line (`:64-85`). A setting typed away from the others is therefore written in the settings block, and its position in the text differs from its position among the file's children.
- So for a text *T*, "parse, then write" can give a different text. The plan calls it the **normalized text** *N(T)* (§4.12).

### 2.4 TH2 writer

- `TH2FileWriter.serialize` builds the text by string concatenation, recursively through `serializeElement` and `_childrenAsString` (`th2_file_writer.dart:35-60, 243-320, 429-439`). It records no element-to-line information.
- Output is produced in the same order as the final text, but **not through one helper**. Some functions produce text (the **leaves**) and others only assemble what leaves return (the **composers**):
  - `_elementOriginalLineRepresentation(element)` (`:322`) returns the stored source text, or `''` when there is none or `useOriginalRepresentation` is false. With `useOriginalRepresentation: true`, which text mode and Save always use, **most lines come from here**. `_serializeScrap`, `_serializeArea`, `_serializeLine`, `_serializePoint`, `_serializeLineSegment`, the three settings serializers and `_serializeMultiLineCommmentContent` call it directly, not through `_prepareLineWithOriginalRepresentation`.
  - `_prepareLine(line, thElement)` (`:467`) generates a line, and can wrap a long line into several. It is used only for elements with no stored text, meaning ones created or changed in Mapiah.
  - `_prepareLineWithOriginalRepresentation(newText, thElement)` (`:123`) is a composer: it returns `_elementOriginalLineRepresentation`, or `_prepareLine` when that is empty.
  - These leaves build their chunk without either helper:
    - the synthesized `encoding` line (`:52`);
    - both branches of `_serializeEmptyLine` (`:143-149`), which reads `originalLineInTH2File` directly;
    - the generated branches of `_serializeMultiLineCommmentContent` (`:151-160`), `_serializeXTherionConfig`, `_serializeXTherionImageInsertConfig` and `_serializeMapiahImageInsertConfig` (`:181-241`). For an image that XTherion can represent, `_serializeMapiahImageInsertConfig` only delegates to `_serializeXTherionImageInsertConfig` with the temporary element (§2.3), so that call is the leaf;
    - line-point option lines in `_linePointOptionsAsString` (`:546-573`), from `_commandOptionOriginalLineRepresentation` (`:542`) or generated. They are written for the **line segment** that owns them.
  - The other composers are `serializeElement`, `_childrenAsString`, `_serializeAllXTherionConfigs` and `_trySerializeXTherionConfig`. Each appends its leaves' results in the order it calls them, and never discards or reorders one.
- An `originalLineInTH2File` can hold several parser lines. It keeps each line's original `\r\n` or `\n` ending, and the writer returns it as is (`_serializeEmptyLine` returns it whole). A lone `\r` remains inside a parser line (§2.3). The `lineEnding` parameter of `serialize` only applies to generated lines.
- Saving uses `_encodedFileContents()` → `toBytes(_th2File, includeEmptyLines: true, useOriginalRepresentation: true)` (`th2_file_edit_controller.dart:1648-1657`). `toBytes` encodes with the file's encoding and line ending.

### 2.5 Model, commands and sub-controllers

- `TH2FileEditController._basicInitialization(file)` (`:669-717`) stores `_th2File` and creates about 20 sub-controllers. It installs no reactions. The reactions, including the dirty-mirroring one, are installed by `_initializeReactions()`, which `_finalFilePreparations` calls (`:827-840`) at the end of a load or for a new file. Many keep their own `TH2File _th2File` field (for example `MPUndoRedoController`, `TH2FileEditSelectionController`, `TH2FileEditCopyPasteController`, `TH2FileEditSearchController`, `TH2FileHideElementController`). **Replacing the `TH2File` object would leave them pointing at the old one.** The apply command replaces its contents in place (§4.7).
- **A broken load skips most of `_finalFilePreparations`** (`:827-864`). When `_isBroken`, it doesn't set `_activeScrapID`, call `updateHasMultipleScraps()` or `snapController.setSnapTargets(...)`; and it returns right after `_initializeReactions()`, before `selectionController.clearIsSelected()`/`setIsSelected(...)`, `resetSelectableElements()`, `updateEnableSelectButton()` and `elementEditController.initializeUsedTypes()`. A broken file's controller has never run that canvas setup.
- **Elements point back at their file.** `MPTH2FileReferenceMixin` keeps a `TH2File? th2File` on every element and option; `TH2File.addElement` sets it (`th2_file.dart:382-388`). `TH2File.forCWJM`, and so `fromMap` and `copyWith`, adds elements to the map **without** setting it. `setTH2File` of `THScrap`, `THArea` and `THLine` returns early when `this.th2File == th2File` (`th_scrap.dart:336-345`, `th_area.dart:331-340`, `th_line.dart:509-521`), before passing the file to options and children. `TH2File.==` is a **deep value comparison** of mpID, filename, encoding, children and elements (`th2_file.dart:158-171`), not identity. So two different `TH2File` objects with the same MPID, filename and elements count as the same file there.
- **Line ending.** The parser sets `TH2File.lineEnding` from the first line break it sees while reading the `encoding` line (`_isEncodingDelimiter`, `th2_file_parser.dart:2973-2987`). Otherwise it stays at the platform default. The writer uses it only for generated lines (§2.4).
- Generic commands exist to build on. `MPAddElementCommand` (with `elementPositionInParent`, undo = `MPRemoveElementCommand`) and `MPRemoveElementCommand` (undo re-adds only the removed element at its position, not its recursively removed descendants). Type-specific add/remove commands exist for points, lines, areas, scraps, line segments, area border thIDs and empty lines. `MPMultipleElementsCommand` wraps several commands into **one** undo step. There is no generic "replace this element, keeping its MPID and children" command. `TH2File.substituteElement(newElement)` (`th2_file.dart:323`) does the replacement without undo.
- Elements have `copyWith(mpID:, parentMPID:, …)` (for example `THPoint.copyWith`, `th_point.dart:153`).
- Undo commands (`lib/src/commands/`) refer to elements by MPID. `enableSaveButton => !_isBroken && _hasUndo && !_th2File.isNewFile` (`:532`) is the TH2 dirty signal. `_actualSave` currently clears the undo/redo stack **before** `writeAsBytesSync` (`:1785-1791`), so a failed write loses the undo history and dirty signal. The save path must clear them only after a successful write (§4.8).
- **Undo and redo don't refresh controller state.** `TH2FileEditController.execute(command)` (`:1806-1811`) runs `updateControllersAfterElementEditPartial`/`Final` after a command. `MPUndoRedoController.undo()` and `redo()` (`mp_undo_redo_controller.dart:115-170`) don't: they run the stored command, set the state to `selectEmptySelection` and redraw. Existing commands get their refresh another way: each `_actualExecute` calls an `execute*` method of the element edit controller that refreshes what it changed itself. For example, `MPMoveElementsCommand` calls `executeMoveElements` (`th2_file_edit_element_edit_controller.dart:1397-1434`), which updates the selection, the selectable elements, the snap targets and the station cache, redraws and bumps the structure revision. Undo runs the inverse command's `_actualExecute`, so the refresh happens in both directions.
- `initializeUsedTypes()` (`th2_file_edit_element_edit_controller.dart:133-166`) adds every element's type to the used-type counts and resets the type for new elements. It isn't idempotent: running it again counts every type again.
- `TH2File.clear()` (`th2_file.dart:773-790`) resets the element map, children, thID registries and derived caches.
- A reaction mirrors `enableSaveButton` into `THProjectController.dirtyFilePaths` (`:1031-1047`), under the canonical path of `_th2File.filename` at the time it fires. `enableSaveButton` is a plain getter (`:532`), and `TH2File.isNewFile` a plain field (`th2_file.dart:41`), not an observable, so the reaction tracks only `_isBroken` and `_hasUndo`: setting `isNewFile` re-runs nothing. It fires only when the value changes, so `MPGeneralController.renameFileController` moves a dirty mark from the old path to the new one when it renames a TH2 controller (`mp_general_controller.dart:615-629`, since `07d83627`). Save As depends on that: it renames the controller before `_actualSave` clears the undo stack, so the reaction then removes the mark from the new path. `t3909` covers this. `THProjectController._saveTH2ProjectFile` (`th_project_controller.dart:1548-1612`) skips a TH2 file whose `enableSaveButton` is false. It serves `saveProjectFile` and `saveAllModifiedFiles` (`:1615`), which saves every path in `dirtyFilePaths`. In this plan, **Save All** means that controller method: no page, menu or shortcut calls it today, only tests (`t3873`, `t3923`). `MPGeneralController.shouldKeepTablessTH2Controller` (`:193-212`) also uses it.
- **There is no unsaved-changes guard.** Nothing asks before unsaved edits are dropped. Closing a tab disposes its controller unless `shouldKeepTablessTH2Controller` keeps it (`removeFileTab`, `mp_general_controller.dart:161-187`), and it never keeps a file with unsaved changes. Closing the window only saves its placement (`MPWindowPlacementController.saveAndClose`, `mp_window_placement_controller.dart:216`). Reload replaces the controller without asking (`reloadTH2File`, `:506-514`). `THProjectController.hasUnsavedChanges` exists but only tests read it. This applies today to canvas edits and to `thconfig`/`.th` tabs alike.
- **Run Therion's broken-file warning.** Since `fe67387a` (#32), the _Run Therion_ dialog warns about the loaded project's broken `.th2` files when it opens (`mp_therion_run_dialog_widget.dart:70-72`). It takes them from `MPGeneralController.loadedBrokenProjectTH2FilePaths()` (`mp_general_controller.dart:437-457`), which lists the registered, loaded project controllers whose `isBroken` is true and that have no load error. Therion reads the files on disk, and running it saves nothing first.

### 2.6 Selection and _Line edit_ mode

- `TH2FileEditSelectionController.mpSelectedElementsLogical` (`ObservableMap<int, MPSelectedElement>`) holds the selected points, lines and areas. `_selectedEndControlPoints` (`:113`) holds the selected line points in _Line edit_ mode, set with `setSelectedEndControlPoint(...)` (`:527`) and cleared with `clearSelectedEndControlPoints()` (`:540`). `selectedScrapMPIDs` holds selected scraps.
- The element tree selects an element with `controller.setActiveScrapByChildElement(element)` followed by `selectionController.setSelectedElements([element], setState: true)` (`th2_element_tree_row_widget.dart:580-595`). It leaves creation modes first with `stateController.onButtonPressed(MPButtonType.select)` (`:481-491`).
- **Tree clicks** are handled by `_onTap` (`th2_element_tree_row_widget.dart:493-576`), which changes only canvas state. A scrap row makes that scrap active, or with Ctrl toggles its selection. An element row selects the element (single tap), adds or removes it (Ctrl), or adds a range (Shift). A second tap on the same row runs `_applyDoubleTapExtras` (`:598-607`), which zooms to the selection with `requestZoomToFit`.
- **Opening a row's context menu** runs `_onBeforeOpenMenu` (`th2_element_tree_row_widget.dart:609-624`) first. On an element row, it leaves creation modes and, unless the element is already selected, selects it as a single tap does. On a scrap row, it does nothing.
- **Which elements a tree action acts on.** The context menu's actions (`_menuSelection`, `:626-641`) and a drag (`_dragPayload`, `:241-270`) act on the whole canvas selection when the row is part of it, and on the row's element alone otherwise. Scrap rows use the selected scraps the same way. The tree highlights the rows of the canvas selection, or the active scrap's row when no scrap is selected (`_isHighlighted`, `:273-290`).
- A double-click enters _Line edit_ mode with `selectionController.setSelectedElements([parentLine])` followed by `stateController.setState(MPTH2FileEditStateType.editSingleLine)` (`mp_th2_file_edit_state_select_non_empty_selection.dart:250-261`).
- `requestZoomToFit(MPZoomToFitType.selection)` exists (`th2_file_edit_controller.dart:1499`). There is no "pan to show without zooming" helper.
- **Element-tree edits.** The tree changes the model through drag and drop (`lib/src/widgets/th2_element_tree_drag_controller.dart:287-315`, `moveElements`), drawing-order actions and _Move to scrap_ (`th2_element_tree_row_widget.dart:795-836`), and the scrap context menu's Cut, Duplicate and Delete (`th2_element_tree_row_widget.dart:717-764`). The project file row's Add scrap action (`th_project_tree_node_widget.dart:128-139`) starts a canvas creation mode that later changes the model. All these actions call `MPGeneralController.prepareTH2FileForTreeEdit(th2FilePath)` (`mp_general_controller.dart:112-128`). The scrap context menu's Copy also calls this gate, although it only reads the model: Copy, Cut, Duplicate and Delete share one method, `_executeScrapEdit` (`:747-764`), which calls the gate before switching on the action. The scrap context menu's _Scrap options_ (`_showScrapOptions`, `:766-785`) instead calls `prepareTH2FileForTreeOptions`, which activates the tab without leaving creation modes, and then opens an overlay window on the canvas through `whenTreeCanvasReady` (`:76-89`). That helper waits a fixed number of frames for the canvas to be laid out and gives up silently. The overlay's option edits change the model through commands. The gate returns `null` to refuse an action (no loaded controller, a broken file, a load error), and otherwise activates the file's tab and leaves creation modes. Each caller returns without doing anything on `null`.
- The edits validate their MPIDs against the **current** model when they run. `moveElements` re-runs `checkMoveElements` (`th2_file_edit_element_edit_controller.dart:1374-1394`), whose `TH2HierarchyAux.validateMove` rejects an unknown element or target parent. `previewDrawingOrderAction` rejects an unknown element (`:1469-1474`). The row actions compute their MPIDs after the gate (`_menuSelection`, `th2_element_tree_row_widget.dart:626-641`), and check that the row's element still exists. So an MPID that disappears before the edit runs makes it a rejection, not a crash.

### 2.7 Keyboard shortcuts

- The edit page uses only `F1` among the function keys (`th2_file_tabs_page.dart:1085`). Function keys have no default meaning in Flutter's text-editing shortcuts on any platform. `F2` is free.
- **Redo is `Ctrl+Shift+Z` everywhere.** This was changed on its own, ahead of this plan. The canvas key handler (`mp_th2_file_edit_state_key_down_mixin.dart`) maps `Ctrl/Cmd+Z` to undo and `Ctrl/Cmd+Shift+Z` to redo. `Ctrl+Y` no longer does anything. The text editor maps the same keys for both Ctrl and Cmd. The redo tooltip, the help pages and the shortcut tables say `Ctrl+Shift+Z`. It is covered by `test/t3956_redo_ctrl_shift_z_test.dart`.

## 3. User-Facing Behavior

### 3.1 Switching modes

- A **Text** button is added to the top-right button group of a `.th2` tab's canvas. That group is part of the canvas (§2.2), so text mode doesn't show it: the text view has its own **Canvas** button, in its toolbar. Both are bound to **`F2`**. The page-level shortcut map that already handles `F1` gets `F2`, so the key works whether the canvas or the text field has focus. On the broken-file body, `F2` does what its _Edit as text_ button does (§3.7).
- In text mode, the tab shows only the text view. The canvas's button groups go with the canvas, and the last-used point/line/area chips and the bottom status bar (§2.2), which describe and drive the canvas, are hidden too.
- Activating a tab that is in text mode (tab switch, opening it again, a tree click) puts the keyboard focus in its text field, so the user can type at once.
- **Entering text mode** first leaves any creation or operation state, as the element tree does (§2.6), except _Line edit_ mode, whose selected line points are used for the cursor (§3.2). An unfinished line or area being drawn is ended the same way `Esc` ends it. Open overlay windows are closed.
- Before changing modes or leaving the current canvas state, check the text source (§4.2) for a lone `\r`. If one exists, keep the current canvas or broken-file view and show a localized message that text mode does not support this file's line endings; the user can normalize the file externally and reload it. Do not normalize the source silently.
- **Leaving text mode** with unchanged text only maps the cursor to a selection (§3.3), or, for a broken file, returns to the broken-file body (§3.4). Changed text is parsed and applied first (§3.4); the mode switch waits for the apply result and stays in text mode if validation rejects the text.
- A **Discard text changes** action (a choice in the "can't apply" message, and the text view's toolbar button that `thconfig`/`.th` tabs use for Revert, with its own tooltip in TH2 text mode) drops the text edits and returns to the canvas with the model untouched, or to the broken-file body for a broken file. Like Revert, the button is enabled only when the text has changed.

### 3.2 Graphical → text

1. Generate the text with the save path (§4.2) and record, for each element, the lines it occupies (§4.3).
2. Collect the selected MPIDs: the selected points, lines and areas, the line segments of any selected line points, and selected scraps.
3. If that set is empty, keep the text view's last scroll position for this tab, or the top of the file the first time. In _Line edit_ mode with no line point selected, use the line being edited.
4. Otherwise, take the **smallest start line** among them. That is the first selected element or line point in file order, whatever order they were selected in. Scroll it into view, and put the cursor at its first non-blank column. Nothing is selected in the text.

### 3.3 Text → graphical (selection)

The cursor line is mapped to an element (§4.4), and then:

| Cursor is on | Result on the canvas |
|---|---|
| a `point` line, or a wrapped continuation of one | the point is selected; its scrap becomes active |
| a `line` header line or `endline` | the line is selected; its scrap becomes active |
| a line point, or one of that point's option lines (`smooth`, `subtype`, …) | _Line edit_ mode opens on the owning line with **that line point selected**; its scrap becomes active |
| an `area` header line, an area option line, a border reference or `endarea` | the area is selected; its scrap becomes active |
| `scrap`, `endscrap`, or an empty line or comment inside a scrap | that scrap becomes active; the selection is cleared |
| anything at file level (`encoding`, settings, comments, empty lines) | the selection is cleared; the active scrap is kept if it still exists, or else the first scrap is used |

Together with §3.2, this makes a selected line point **round-trip**. Going to text puts the cursor on its line, and coming back with the cursor still there selects it again in _Line edit_ mode.

If the selection is outside the visible canvas area, the canvas is centered on it at the current zoom (§4.9). Nothing is zoomed.

### 3.4 Text → graphical (apply)

- If the text is unchanged since entering text mode, nothing is parsed or applied; the line map from §3.2 is used in reverse. A broken file's session has no writer line map (§4.2), so unchanged text there returns to the broken-file body with nothing selected, as _Discard text changes_ does. If the text changed but normalizes back to the initial text (§4.12), for example after typing a duplicate line point, nothing is applied, but the raw cursor line is mapped to the initial writer text before resolving selection.
- If the text changed, the whole new text is parsed into a detached model first (§4.5).
  - **Unsupported lone `\r`:** reject the buffer before parsing it if a lone `\r` got into it, for example from pasted text. Mark the containing editor line, keep the current model and undo stack, and offer the same _Keep editing_ and _Discard text changes_ choices as other rejected text. Save and tree edits that require an apply are blocked too.
  - **Characters the file's encoding can't hold:** treated like a problem (next item). Each such line gets a blocking diagnostic naming the encoding, because Save could not write it (§4.2).
  - **Any error or problem:** nothing is applied. The tab stays in text mode. Each `TH2FileProblem` is marked at its line, and errors without a line number are listed in a message above the editor. The message offers _Keep editing_ and _Discard text changes_.
  - **No errors and no problems:** the final normalized text becomes one command on the canvas undo stack (§4.6). The canvas, the element tree and the dirty state update. The cursor line is then mapped on the updated model (§4.4, §4.12).
- Lines the parser will rewrite or drop don't block the apply. They carry information markers while the user edits (§4.12), and the model gets the normalized text.

### 3.5 Undo

- **In text mode**, undo and redo work as in the `thconfig`/`.th` editor: `Ctrl+Z` and `Ctrl+Shift+Z` use the `TextField`'s own history, which groups typing by 500 ms pauses (§2.1). They reach back only to the start of the text session, or to the last save (§3.6). Neither action changes the canvas model until an apply.
- **On the canvas**, one successful text apply is one undo step, regardless of how many lines were changed, how often the cursor moved, or how many text-editor undo/redo actions occurred. `Ctrl+Z` restores the exact model from before that apply; `Ctrl+Shift+Z` restores its result. Older canvas commands remain below it on the same undo stack (§4.7).
- Leaving text mode or saving applies the current final text once. If it is unchanged, or normalizes to the initial text, no canvas command is added. If it does not parse, nothing is applied and the editor remains open (§3.4).

### 3.6 Save in text mode

Save (the app bar button, the overflow menu, the text view's toolbar button, `Ctrl+S`, and the project controller's Save All, §2.5) is enabled under the same rule in both modes, `canSave` (§4.8), and awaits the text apply of §3.4 before saving through the normal TH2 path. **If the text doesn't parse, nothing is written**, and the problems are shown as in §3.4. Mapiah never writes a `.th2` file it can't read back. The tab stays in text mode after a successful save, and the text is regenerated from the saved model. This is the normalized text, exactly what was written, so lines the parser rewrote or dropped show their saved form. The cursor line is kept through the mapping in §4.12.

The regenerated text **starts a new text session**, also when the edited text normalizes back to the text from before the edits, so nothing was applied (§3.4, §4.6): the buffer then shows the saved text and no longer counts as unsaved. It must not enter the `TextField`'s undo history: setting it programmatically would add it as one more entry, and `Ctrl+Z` right after the save would bring back the text from before the save. The history can't be cleared through a public API, so `TH2TextEditBodyWidget` keys `THTextEditorWidget` with the text session's number. A new session builds a new `TextField` with an empty history, and the cursor line is restored through `pendingScrollToLine`/`pendingSelectionRange`.

If the write fails after the text was applied, the tab still gets a new session from the applied model, as after a successful save (§4.6). The applied model is what a retry writes, so a retry has no text left to apply and adds no second canvas undo step.

**Save As** checks the text before the file picker opens, but applies it only after the user confirms a file name. Text that doesn't parse is refused, as for Save, and no picker opens. Cancelling the picker changes nothing: the model, the canvas undo stack, the text and its `TextField` history stay as they were. Confirming applies the text (one canvas undo step), writes the file and starts a new text session, as Save does (§4.8). While the picker is open, leaving text mode, Save and tree edits on that tab wait for Save As to finish, and tree clicks do nothing (§4.8).

### 3.7 Broken files

The broken-file tab body (`TH2BrokenFileBodyWidget`) gets an **Edit as text** button. It opens text mode with the **raw file content from disk**, decoded with the file's encoding. It can't use the writer, because a broken model is missing the lines the parser dropped. The problem list is shown as line markers. Applying or saving works as in §3.4 and §3.6. Save applies the text before the check that today refuses to save a broken file (§4.8). Once the text parses cleanly, the controller stops being broken, and the canvas becomes available: leaving text mode then shows the canvas, not the broken-file body (§4.1).

A broken model can't be compared line by line with the fixed text, because the model doesn't match the disk text. So the first apply of a broken file replaces the whole model. That replacement is a **new baseline, not an undo step**, like a file load (§4.7). A canvas `Ctrl+Z` can never bring back the broken, incomplete model, because Save would then write a file that is missing the lines the parser dropped. The fixed file counts as unsaved until it is saved. To go back to the broken state, the user reloads the file from disk. After that, the file is valid, and later text sessions each apply as one canvas undo step (§4.6).

### 3.8 Element-tree edits in text mode

The element tree stays usable while a tab is in text mode. Its edits (drag and drop, drawing order, _Move to scrap_, Cut, Duplicate and Delete) change the model, which the text doesn't show yet. So a tree edit **applies the text first**:

1. If the text changed, it is applied as when leaving text mode (§3.4): one canvas undo step.
2. If the text doesn't parse, nothing is applied and the tree edit is **cancelled**. The tab stays in text mode with the problems marked and the "can't apply" message (§3.4), so the user sees why the drop or the menu action did nothing.
3. Otherwise, the text buffer becomes temporarily read-only, starting synchronously when validation accepts the current buffer, before any apply changes the model. Scrolling, text selection, find and copy remain available; typing, paste, cut, indentation, replacement and text undo/redo are blocked until the operation finishes. The tree edit runs on the applied model, as its own canvas undo step. An element the edit names that the apply removed or replaced (§4.7) makes the edit a no-op, as for any stale tree row.
4. The tab stays in text mode. The text is regenerated from the model, as after a save (§3.6), and starts a new text session. This happens once, after the tree edit, whether the edit ran or was a no-op: after an apply, the old session no longer describes the model (§4.6). The cursor stays on the element it was on, or the nearest line if that element is gone. If the tree action sets a selection, the cursor goes to the first selected element in file order, as in §3.2.

A tree edit made with unchanged text skips steps 1 and 2, but its buffer is still read-only while the edit runs (step 3): the edit's command starts a new text session, which would drop text typed meanwhile. The project file row's _Add scrap_ first follows the same apply gate, then switches the tab to canvas and starts the creation mode there. If apply is rejected or cancelled, it stays in text mode and starts no creation. _Copy_ is read-only: it uses a separate read-only tab-activation path and does not apply the text or start a new session. So in text mode it copies the scraps as the model has them, without the text edits that haven't been applied yet, and preserves the canvas selection, selected line points, active scrap, editing state and tree highlights. On the canvas, Copy still leaves creation modes first, as it does today (§4.13).

The scrap context menu's _Scrap options_ is **disabled** while the tab is in text mode. Its overlay window belongs to the canvas, which text mode hides (§2.6), and the scrap's options can be edited in the text itself.

### 3.9 Tree clicks in text mode

While the tab is in text mode, a click on a tree row moves the **text cursor**, not the canvas selection:

- A click on an element row puts the cursor on that element's first line, at its first non-blank column, and scrolls it into view, as §3.2 does for a selection of that one element. A click on a scrap row does the same with the `scrap` line.
- Ctrl and Shift clicks behave as plain clicks, and a second tap doesn't zoom. The canvas selection, the active scrap and the zoom stay as they are. They would be replaced anyway when the tab returns to the canvas, because the cursor line decides the selection then (§3.3).
- If the text has been edited, the element's line is followed through the edits to its line in the current text. If that line was itself edited, the cursor goes to the nearest unedited line above it (§4.14).
- The text field gets the keyboard focus, so the user can type at once.
- The click doesn't apply the text, change the model or start a new text session. While an apply is pending (§4.6), a click is ignored.
- **Opening a row's context menu** (right-click) moves the text cursor to the row's element or scrap in the same way, before the menu opens. The text field gets the focus when the menu closes. It doesn't select the element on the canvas or leave a creation mode, as it does on the canvas (§2.6). The menu's actions then act on the elements §2.6 describes: the highlighted rows if the row is one of them, or the row's element alone. While the tab is in text mode, the highlighted rows are the canvas selection from before text mode was entered, since clicks and the context menu don't change it. Only a tree edit that sets a selection does (§3.8, step 4).

## 4. Design Decisions

### 4.1 Mode lives on `TH2FileEditController`, text state on a new `TH2TextEditController`

- `TH2FileEditController` gains `@observable TH2EditMode editMode` (`canvas`, `text`) and `@readonly TH2TextEditController? _textEditController`. The text controller is created when text mode is first entered, and dropped when the tab's controller is disposed.
- `TH2FileEditBodyWidget` shows `TH2TextEditBodyWidget` when `editMode == text`, and otherwise the canvas or the broken-file body. The mode is per tab, because it belongs to the tab's controller. It survives tab switches, and project-tree clicks don't reset it.
- **Choosing the body.** Once the load future has data, the body decides from the controller alone, inside an `Observer`: `editMode`, then `isBroken`. The `snapshot.data!.problems.isNotEmpty` test (§2.2) is removed. The load result is cached and never changes, so after a broken file's fix is applied (§4.7) it would keep showing the broken-file body. `_commitLoadResult` already sets `_isBroken` whenever the result has problems, so a load shows the same body as today. The last-used chips and the status bar below it are shown only when the file isn't broken **and** `editMode == canvas`, in the same `Observer`, so they also appear once a fix is applied.
- **Mode buttons.** The canvas's top-right group (`TH2FileEditActionButtonsWidget`) gets the _Text_ button. `TH2TextEditBodyWidget` passes a _Canvas_ button to `THTextEditorWidget` through a new optional `leadingToolbarActions` list, shown at the start of its toolbar; `thconfig`/`.th` tabs pass none. The broken-file body's _Edit as text_ is its entry button (§3.7). The page's `F2` handler calls `TH2FileEditController.toggleEditMode()`, which runs `enterTextMode()` or `leaveTextMode()`, the same calls as the buttons; on a broken file outside text mode it opens the raw text, as _Edit as text_ does.
- **Focus.** `TH2FileEditController` gains `FocusNode get activeFocusNode`: the text controller's `textEditorFocusNode` while `editMode == text`, and `th2FileFocusNode` otherwise. The three tab-activation sites (§2.2) request focus on it instead of on `th2FileFocusNode`. Entering text mode focuses the text field, and leaving it focuses the canvas, once the new body is built.
- **Closing the tab ends text mode.** When a tab is closed, its controller is either disposed, along with the text controller, or kept without a tab (`shouldKeepTablessTH2Controller`, §2.5). It is only kept when it has no unsaved changes, which includes unchanged text (§4.8). A kept controller would otherwise stay in text mode with no editor on screen: tree clicks would move the cursor of a hidden editor (§4.14), and reopening the tab would show an old session. So `MPGeneralController.removeFileTab` calls a new `TH2FileEditController.onTabClosed()` on a controller it keeps. That method ends the text session, drops the text controller and sets `editMode` to `canvas`. It changes no model and runs no apply, since the text is unchanged. Reopening the tab shows the canvas.
- A split view could later show both widgets. The single `editMode` value would then become two visibility flags.

### 4.2 The text source

- **Valid file:** a new `TH2FileEditController.serializeForTextMode()` uses `TH2FileWriter().serializeWithLineMap(_th2File, includeEmptyLines: true, useOriginalRepresentation: true)` and keeps its line endings as they are. The writer checks its assembled output for a lone `\r` before scanning it into a line map; if found, it throws a typed unsupported-line-ending exception, which `enterTextMode` catches for the §3.1 refusal path. The method shares its writer options with `_encodedFileContents()`, so the two can't drift apart. `TH2TextEditController.initialContent` keeps this text for dirty and no-op checks (§4.6).
- **Broken file:** the raw bytes from disk (or `_th2File.fileBytes` when it's set), decoded with the parser's encoding detection, which becomes a public static helper. Today `_encodingNameFromFile` can't simply become static: through `_isEncodingDelimiter` (`th2_file_parser.dart:2973-2987`) it also sets `_parsedTH2File.lineEnding`. The helper therefore returns the encoding name together with the line ending it saw, if any, and the parser assigns `lineEnding` from that result. Load behavior doesn't change.
- **Unsupported lone `\r`:** `TH2TextLineEndingsAux` (new, pure) has a check for `\r` not followed by `\n`, and splits text into lines at `\r\n` and `\n` the way the parser does. Run it on the decoded raw source of a broken file and the writer output of a valid file before starting a text session. Run it again on the current buffer before idle validation or apply; the entry check alone cannot cover characters introduced later. A failed check returns a refusal or diagnostic with a localized message, without parsing, changing the model, or writing bytes (§3.1, §3.4).
- **Original line endings.** Mapiah only changes what the user edited, so files kept under version control show no spurious differences. Text mode keeps that rule for line endings by keeping them **in the editor buffer itself**:
  - The buffer is the raw text, with each line's real ending: the writer output for a valid file, the decoded disk text for a broken file. Nothing converts it to a single ending, and there is no separate record of endings.
  - Editing a line's content leaves its ending in place, so an **edited line keeps its ending**. Pasted text is inserted as it is, so a **pasted line keeps the ending it was pasted with**. Enter always inserts the file's default line ending (`TH2File.lineEnding`, §2.5), as lines created on the canvas get today (§4.9). It does not inherit the ending of the current line: in a mixed-ending file, splitting an LF line in a file whose default is CRLF inserts CRLF, and splitting a CRLF line in a file whose default is LF inserts LF. The existing ending on the remaining part of the line stays unchanged. A pasted lone `\r` is rejected by the check above.
  - Lines are counted at `\r\n` and `\n` everywhere in text mode. The widget already counts `\n`, so a `\r\n` line is one line (§2.1). Unicode treats `\r\n` as one character (grapheme cluster), so the cursor moves over it as one. The TH2 tokenizer and folds treat a `\r` at the end of a line as part of its ending (§4.10).
  - The buffer goes to the detached parse as a string, through a new `contents` parameter of `TH2FileParser.parse` (§4.5), so it isn't encoded and decoded again. The parser takes the encoding name from the text's own `encoding` line, with the same rules as the byte-based detection, or the default encoding when there is none. It sets `TH2File.lineEnding` with the same rule as `_isEncodingDelimiter` too (§2.5): the first line break among the first `mpthMaxEncodingLength` characters, read from the text instead of the bytes, or the platform default when there is none, as a load does. `replaceContentsFrom` copies the detached file's `lineEnding` into the live file (§4.7), so without this a CRLF file would switch to the platform default after an apply, and Enter and generated lines would then use it. The parsed elements then store each line with its text and ending, so the writer reproduces every line exactly, including mixed endings. A save changes only the lines the user edited, typed or pasted.
  - **Encodability.** The user can type characters that the file's encoding can't hold, such as `ç` in an `ASCII` file. `toBytes` would then fail on Save: `ascii.encode` and `latin1.encode` throw. So validation also checks that every line of the buffer can be encoded with the encoding of the detached model, the one Save will use. `toBytes`' encoder choice moves into a shared helper of `TH2FileWriter`, so the check and Save can't disagree. A line that fails gets a blocking diagnostic (§3.4).
  - Undo and redo keep the bytes too, because the snapshots store each element's `originalLineInTH2File` (§4.7).
- **Comparisons.** Whole-text comparisons use the raw text: `isDirty`, the "text unchanged" test in §3.4 and the no-op check in §4.6. So a change of a line's ending alone, such as pasting a line over an identical one with another ending, counts as an edit and is applied. Line-level comparisons (identity matching, §4.7, normalization markers, §4.12) compare lines without their endings, so such a line still matches for MPID matching and gets no normalization marker.

### 4.3 Writer line map (model MPID → line range)

`serializeWithLineMap` returns `(String text, TH2TextLineMap lineMap)`. It uses a **line ledger**:

- A single private `_emit(int mpID, String chunk)` returns `chunk`. In ledger mode, when `chunk` isn't empty, it appends `(mpID, startOffset, chunk.length)` to the ledger, where `startOffset` is the total length of earlier emitted chunks. The offset is in the writer's output, which is also the editor text (§4.2). This also records a final line with no line ending, which counting line endings alone would miss.
- `_emit` goes in the **leaf producers only** (§2.4):

  | Leaf | Attributed to |
  |---|---|
  | `_elementOriginalLineRepresentation(element)` | the element |
  | `_prepareLine(line, element)`, including every part of a wrapped line | the element |
  | `_commandOptionOriginalLineRepresentation(option)` and the generated option line in `_linePointOptionsAsString` | the line segment (`option.parentMPID`) |
  | the generated branches of `_serializeXTherionConfig`, `_serializeXTherionImageInsertConfig`, `_serializeMapiahImageInsertConfig` and `_serializeMultiLineCommmentContent` | the element. An image written in XTherion format goes through `_serializeXTherionImageInsertConfig` with the temporary element (§2.3), whose MPID is the model element's, so its line is attributed correctly |
  | both branches of `_serializeEmptyLine` | the empty line |
  | the synthesized `encoding` line | the file |

- Composers (`_prepareLineWithOriginalRepresentation`, `serializeElement`, `_childrenAsString`, `_serializeAllXTherionConfigs`, `_trySerializeXTherionConfig` and the per-type serializers) get **no** `_emit`. `_prepareLineWithOriginalRepresentation` in particular only delegates, so an `_emit` there would count every generated line twice.
- **Rule**, stated in a comment on `_emit`: a leaf's result is appended to the output exactly once, in the order the leaf was called, and never thrown away or reordered. The current writer follows it: every composer computes a header before its children, and a line segment before its option lines.
- **MPID check.** In ledger mode, `_emit` asserts that `mpID` names an element of the file being written, or the file itself. A future temporary element built with a fresh MPID, instead of reusing the model element's as the #46 image conversion does, then fails the fixture test instead of producing lines that belong to no element.
- **Length check.** In ledger mode, `serializeWithLineMap` asserts that the ledger's offset spans are contiguous and their lengths add up to the output's length. This catches a chunk that bypasses `_emit` without a line ending (such as one part of a wrapped line), a chunk that is counted twice, or a chunk that is recorded but never appended.
- Output order equals text order. Scan the output once for line starts, treating `\r\n` and `\n` as line endings; text-mode entry has already rejected a lone `\r` (§4.2). Each nonempty ledger span owns the lines containing its characters; an ending belongs to the line before it. Thus a final chunk without an ending still owns its final line, while a trailing ending doesn't create another owned line. These lines are numbered from 0, as editor lines. An element's **own lines** are the lines of its ledger spans. Its **range** runs from its first own line to the last line of its last descendant.
- `serialize` and `toBytes` keep their signatures and their exact output. Ledger mode is off by default.
- **Empty file.** `serialize` treats a file with no children like a file whose first child isn't an `encoding` line (§2.3): the check becomes `childrenMPIDs.isEmpty || elementByMPID(childrenMPIDs.first) is! THEncoding`. An empty file is then written as the synthesized `encoding` line alone, attributed to the file in the ledger. Output changes only for files that make `serialize` throw today. In text mode, an empty buffer is valid text: its normalized text is that one line, which gets the "Mapiah will add" marker (§4.12), and applying it leaves a file with no scraps.
- A test checks that the ledger's spans cover the returned text exactly, including a final unterminated line, and that `serialize`'s output is unchanged byte for byte. Loaded fixtures only run the "stored text" branches, so the test covers the generated ones too:
  - every fixture in `test/auxiliary/*.th2`, written with `useOriginalRepresentation` both `true` and `false`;
  - a model built with commands, whose elements have no stored text. It includes new settings elements (the `_trySerializeXTherionConfig` path), a file with no `encoding` line, a line long enough to wrap, line-point options with no stored text, and a `##MAPIAH##` image that XTherion can represent, next to one it can't (rotated or scaled).

  An output site that bypasses `_emit`, or an `_emit` in a composer, makes the test fail.

`TH2TextLineMap` (new, `lib/src/auxiliary/th2_text_line_map.dart`) keeps each element's own lines and range, and a sorted `line → owning MPID` array for reverse lookup. Line numbers are 0-based here to match the editor's `cursorLine`. Conversion from the parser's 1-based numbers happens in one place.

### 4.4 Parser line map and ownership resolution

- `TH2FileParser` gains `Map<int, int> elementStartLines` (MPID → 1-based `_currentLineNumber`). It is filled by a private `_addElement(...)` helper that wraps the 21 `executeAddElement` calls. It records only where each element **starts**. Some lines aren't element starts:
  - the continuation lines of a multi-line value: a bracketed or quoted value that continues on the next line, or a line ending with `\` (a joined parseable line keeps the number of its first line, §2.3);
  - line-point option lines (`smooth`, `subtype`, …), which become options of the preceding line segment and have no `executeAddElement` call of their own.

  So an element's own lines are derived: they run from its start line up to the line before the next recorded start line, in file order. A parent's own lines stop before its first child's start line. This attributes continuation lines to the element they continue, and option lines to their line segment, as the writer's ledger does (§4.3). Own lines are derived from **all** recorded start lines, including those of elements that the clean-up passes remove (`_linesCleanUp`, `_areasCleanUp`). The removed elements' lines are then taken out of the map and kept as **removed lines**, each pointing at its removal's normalization record (§4.12). Dropping the entries first would fold a removed element's lines into the element before it, whose raw text would then differ from its written text and get a spurious rewrite marker. The resulting map gives the **raw-text** lines of a detached model's elements. Together with the writer's map of the same detached model, it drives the normalization markers and the raw → normalized cursor mapping (§4.12), so its correctness is load-bearing: `t3962` checks it against the writer's map, including option lines, multi-line values and removed lines. Both maps split lines at `\r\n` and `\n`, after the lone-`\r` check (§4.2). The apply uses the writer's map of the normalized text for selection and identity matching (§4.6, §4.7).
- `TH2TextElementLocator` (new, pure, `lib/src/auxiliary/th2_text_element_locator.dart`) turns a line and a `TH2TextLineMap` into a `TH2TextLocation`, following §3.3:
  1. Find the element that owns the line (the reverse array).
  2. If it's a line segment, or a line-point option line owned by one, return `selectLinePoint(lineMPID, lineSegmentMPID, scrapMPID)`.
  3. Otherwise, walk up `parentMPID` until reaching a `THPoint`, `THLine`, `THArea` or `THScrap`, or the file.
  4. Return `selectElement(mpID, scrapMPID)`, `activateScrap(scrapMPID)` or `fileLevel`.
- The locator is pure and gets its own unit tests. `TH2FileEditController.applyTextLocation(location)` carries the result out on the canvas. It uses the tree's single-tap sequence for `selectElement`, and the double-click sequence plus `setSelectedEndControlPoint` for `selectLinePoint` (§2.6).

### 4.5 Detached parse

`TH2FileParser.parse` gains an optional `TH2FileEditController? targetController`. When it's given, the parser uses that controller instead of looking one up in `MPGeneralController`. It also gains an optional `String? contents`: when given, the parser skips reading and decoding bytes, takes the encoding name from the text (§4.2) and splits `contents` directly. Text mode creates a **scratch controller**, `TH2FileEditControllerBase.createForDetachedParse(filename, th2FileMPID)`. It is never registered and never gets a tab. Its `TH2File` uses the real file's MPID, so top-level `parentMPID`s already point at the real file. The `TH2File()` constructor always takes a new MPID from `nextMPIDForTH2Files()` (`th2_file.dart:80-82`), so `TH2File` gains a named constructor, `TH2File.withMPID(int mpID)`, that sets `_mpID` to the given value instead. Because the scratch file has the real file's MPID and filename, it can be `==` to the live file (§2.5). §4.7 therefore never adopts the scratch file's element objects into the live file. MPIDs come from the global counter (`nextMPIDForElements`), so they can't collide with the live model. The scratch controller is disposed after each parse; the detached file result may be cached independently (§4.6).

`createForDetachedParse` runs only `_create()` and `_basicInitialization`. It never calls `_finalFilePreparations` or `_initializeReactions` (§2.5). The scratch controller shares the real file's filename, so the dirty-mirroring reaction (`:1031-1047`) would otherwise add or remove the real file's path in `THProjectController.dirtyFilePaths`. A doc comment on the factory states this, and an `assert` in `_initializeReactions` rejects a detached controller.

The current editor content gets a detached parse after an idle delay and again at apply if the cached result is stale (§4.6). `TH2FileParser.parse` returns a `Future`, so apply and every operation gated by it must await that parse. The parse validates the final text and supplies the replacement model.

### 4.6 Current-buffer validation and one apply

`TH2TextEditController` holds the current `content`, `initialContent`, cursor position and diagnostics. The `TextField` owns its undo history. No canvas checkpoints are recorded on cursor moves, typing, find/replace, or text-editor undo/redo.

After a change, debounce validation of the **current buffer** by `mpTH2TextValidationIdleMilliseconds`. Reject a lone `\r` before starting a detached parse, with a diagnostic on its containing line (§4.2). Otherwise, check encodability and parse the buffer as it is (§4.2). Cache the result keyed by the exact buffer string it validated: validity, problems, encodability diagnostics, normalization records, normalized text *N(T)*, and the parser and writer line maps of the detached model. If the content changes again, discard the stale result. This gives current problem and normalization markers even when the cursor stays on one line. At apply or Save, reuse the cache only if its content still equals the current buffer; otherwise validate the current buffer before proceeding. An unsupported line ending, a character the encoding can't hold, a parser error or a problem blocks the apply and leaves the model and canvas undo stack untouched (§3.4).

`applyTextContent(String content, {bool lockBufferOnAccept = false})` takes the editor buffer, with its real line endings (§4.2), and returns `Future<TH2TextApplyResult>`. It snapshots the buffer content and text-session revision before awaiting a detached parse (or an in-flight validation of the same content). After the await, it checks that the controller is still live, the same text session is active and the buffer still equals that snapshot. If the controller was disposed or the session changed, it returns `cancelled` without changing the model; if only the buffer changed, it discards the stale result and validates the current buffer before any model change. Concurrent mode switches, apply, Save, Save As and tree-edit requests for one tab are serialized through the same pending-operation gate; a second request rechecks the current buffer after the first finishes. Nothing that depends on apply may run while its result is pending. The final snapshot and command execution are synchronous after validation, so the model cannot change between the accepted parse and the command. When `lockBufferOnAccept` is true, which Save, Save As and `applyTextBeforeExternalEdit` pass (§4.8, §4.13), the operation-owned buffer lock is set synchronously after that final snapshot check and before any model change, including when the result is `unchanged`, and also when the buffer equals `initialContent`, so no parse is needed. Typing remains available while validation awaits; a rejected or cancelled validation acquires no buffer lock.

**Save and Save As lock the buffer after accepted validation.** Both pass `lockBufferOnAccept: true` to `applyTextContent`, including when the text is unchanged. Awaiting its `Future<TH2TextApplyResult>` introduces a microtask boundary after the synchronous apply and before the caller writes and replaces the session, even with `writeAsBytesSync`. A queued mutation in that gap must be blocked so session replacement cannot discard it. The lock belongs to the enclosing operation, independently of the text session: `endSession()` and starting a new session cannot release it. Save and Save As hold it through the awaited apply result, write, commit or rollback, and session replacement, using the same cleanup pattern as `runTH2TreeEdit` (§4.13). An inner `finally` releases the lock and operation gate even when writing or regeneration throws; a disposed controller is never given a new session. Editing remains available while validation awaits and while the Save As picker is open, and rejected or cancelled validation acquires no lock. After cleanup, edits reach the new session normally. `t3987` checks the microtask gap, unchanged text and failure cleanup.

**No general line diff.** Every comparison that the apply, the markers and tree clicks need is answered from information the plan already has, in linear or near-linear time. There are no work or storage ceilings, and no fallback that coarsens results in large files or after large edits:

- identity between the live and the detached model: content-keyed matching of elements (`TH2TextIdentityMatcher`, §4.7);
- raw text *T* ↔ normalized text *N(T)*: the detached model's parser and writer line maps, which share its MPIDs (§4.12);
- `initialContent` ↔ current buffer, for tree clicks: a line tracker fed by each buffer change (`TH2TextLineTracker`, §4.14).

**Rejected alternative:** a general line diff (Myers' O(ND)). Its work grows with the edit size times the file size, and its trace with the square of the edit size, so it needs ceilings. Past them, a fallback loses identity or precision exactly in large files and after large edits, such as deleting or pasting a block of a few hundred lines. It also can't tell a moved element from a deleted and re-added one, which content-keyed matching does.

If the final normalized text equals `initialContent`, the apply creates no canvas command. Otherwise, take a deep `before` snapshot of the live file, match unambiguous unchanged MPIDs into the detached model (§4.7), and take an `after` snapshot. Assert that the remapped model still serializes to *N(T)*. Execute one `MPReplaceTH2FileContentsCommand` through `TH2FileEditController.execute` (`:1806-1811`), with a localized description such as "Text edit". That method passes it to `MPUndoRedoController` and then runs `updateUndoRedoStatus()`, which sets `_hasUndo`, and so `enableSaveButton` and the dirty state (§4.8). Calling `undoRedoController.execute` directly would skip that. The command uses `TH2File.replaceContentsFrom` to update the existing live `TH2File`; undo and redo restore the two snapshots. This makes the final model valid after either action, even if the user passed through incomplete syntax while typing.

The controller refresh (stale selection and hidden MPIDs, selectable elements, active scrap, snap targets, structure revision) is not a step of the apply. It runs inside the command (§4.7), so apply, undo and redo all get it. After a successful apply, the apply itself only maps the final raw cursor line through *N(T)* to the live writer line map and returns it in its result. It does **not** end the text session: its caller does, after the operation it is part of. A leave ends the session (_Ending a text session_, below), and Save, Save As and a tree edit replace it with a new one at the end of their operation (_An apply that stays in text mode_, below). Until then the old session stays open, so the tab in text mode always has a buffer to show, the tree edit's read-only buffer remains visible until its replacement is ready, and its dirty buffer keeps `canSave` true until Save As has renamed the controller (§4.8). The operation gate (§4.6) keeps a second apply from running on that stale session. When the apply leaves text mode, the next entry to text mode starts from newly serialized content.

**Ending a text session.** The text controller outlives its sessions: it is created on the first entry to text mode and kept until the tab's controller is disposed or `onTabClosed()` drops it (§4.1). So ending a session must leave nothing that counts as an edit. `TH2TextEditController.endSession()` drops the session's `content`, `initialContent`, writer line map, diagnostics and its validation cache and line tracker (§4.6, §4.14), and keeps only the last scroll position, which §3.2 step 3 reuses on the next entry. With no session, `isDirty` is false. Every way out of text mode ends the session this way, whatever the apply result: a leave after an `applied` or `unchanged` result, a leave with unchanged text, _Discard text changes_, the return of an unchanged broken-file session to the broken-file body (§3.4), `runTH2TreeEdit` with `leaveTextMode: true` (§4.13), and `onTabClosed()` (§4.1). Starting a new session (§3.6) ends the old one first. Without this, after an `applied` leave the kept buffer would still differ from its pre-apply `initialContent`: `hasUnsavedChanges` would stay true on the canvas after a save, the dirty dot would never clear, and `shouldKeepTablessTH2Controller` would never keep the controller (§4.8).

**An apply that stays in text mode starts a new session.** Save, a tree edit (§4.13) and Save As apply the text and keep the tab in text mode. After an `applied` result, the old session no longer describes the model: its `initialContent` is the text from before the apply, and its line map has none of the new MPIDs. Left in place, the buffer would still count as edited, and the next leave, Save or tree edit would run a second `MPReplaceTH2FileContentsCommand` whose `before` and `after` are the same model. Tree clicks on changed elements would find no line (§4.14). So every operation that applies the text and stays in text mode ends with **one** new text session from the live model (§3.6), whatever its outcome, with the cursor mapped through *N(T)* (§4.12):

- Save: after the write, whether it succeeds or throws, and whether the apply result was `applied` or `unchanged`. An `unchanged` buffer may still differ from `initialContent`, when it normalizes back to it (§3.4, for example after typing a duplicate line point). Keeping that session would leave the buffer dirty, and `canSave` and the dirty dot on, after a successful save, and would keep the `TextField` history from before the save (§3.5).
- Save As: as Save, but not right after the write. After a successful write it comes after `renameFileController` and the commit, and before `isNewFile = false`; after a failed write it comes after the rollback (§4.8). A dismissed picker applies and writes nothing, so it keeps the session (§4.8).
- A tree edit: after the edit, whether it ran a command or did nothing, when the apply result was `applied`, or when the edit ran a command (§4.13). Inside the operation, the new session that `execute` asks for is deferred to this point, so the operation starts one session, not two.

Otherwise, when the result is `unchanged`, `rejected` or `cancelled`, the model wasn't changed, and the session is kept.

### 4.7 Whole-file apply command and broken-file baseline

`MPReplaceTH2FileContentsCommand` (new) holds two deep snapshots, `before` and `after` (`TH2File.toMap()` maps). Add `lineEnding` to `TH2File.toMap()` and require it in `fromMap()`. Update `TH2File.forCWJM` and `copyWith()` to carry the value too, so copying a file doesn't silently reset its line ending. The command's `_actualExecute` calls a new `elementEditController.executeReplaceTH2FileContents(Map<String, dynamic> snapshot)`, following the pattern of the other commands (§2.5). That method runs `TH2File.replaceContentsFrom(TH2File.fromMap(snapshot))` and then `syncControllersWithModel(initialSetup: false)` (below). Apply, undo and redo all run the same `_actualExecute`, with the `after` or `before` snapshot, so all three refresh the controllers in the same way, without any change to `MPUndoRedoController`. The live `TH2File` object never changes, so the sub-controllers' references (§2.5) stay valid. Undo restores `before` with its original MPIDs, so older commands stay valid.

`TH2File.replaceContentsFrom(TH2File source)` (new):

1. Clears the same registries and caches as `clear()` (element map, children, thID registries, type sets, scrap/image/setting lists, area-line maps, bounding box). Unlike `clear()`, it keeps `filename`, `fileBytes`, `mpID` and `isNewFile`.
2. Takes the source's `encoding` and `lineEnding`.
3. Puts **all** of the source's elements into the element map, and copies its `childrenMPIDs`.
4. Only then calls `element.setTH2File(this)` on **every** element, and `_updateSupportMaps(element)`. All elements must be in the map first, because `setTH2FileToChildren` looks children up through the file (`th_is_parent_mixin.dart:82-86`). Calling it on every element, not only the top-level ones, doesn't depend on the parents passing it down.

**Element back-references (§2.5).** The source must be a **fresh `fromMap` copy** whose elements belong to no file (`th2File == null`). Then the early return in the `setTH2File` of `THScrap`, `THArea` and `THLine` can't fire, since `null` never equals the live file. Elements still pointing at another `TH2File` would be the problem: if that file has the live file's MPID and filename, as the scratch file does (§4.5), the deep `==` can find them equal and skip the children and options, which would keep pointing at the scratch file. So:

- No path passes the scratch file, or any element object from it, to `replaceContentsFrom`. The apply command already uses its snapshot maps. The broken-file baseline below uses `TH2File.fromMap(detached.toMap())` as well.
- `replaceContentsFrom` asserts that every source element and option has `th2File == null` on entry, and that every element and option has `identical(th2File, this)` on exit. Both checks use identity, not `==`.

**Controller refresh.** `TH2FileEditController.syncControllersWithModel({required bool initialSetup})` (new) brings every sub-controller in line with the current model. It is the **only** place this is done: a valid load, the broken-file baseline below, and every apply, undo and redo of `MPReplaceTH2FileContentsCommand` call it. In order:

1. **Selection.** Drop the MPIDs that no longer exist from the logical selection, the selected line points (`_selectedEndControlPoints`), the selected scraps (`selectedScrapMPIDs`) and the `isSelected` flags. Rebuild every retained logical selection's clone from the live model with `updateAllSelectedElementsClones()`, including each selected line's cloned child segments. Refresh retained selected line points with `updateSelectedLineSegment`, so their clones and endpoint types reflect the live segments. Keeping an MPID does not imply unchanged geometry or children: a line header can match while its points change. Defer rebuilding selectable elements and control points until the active scrap has been resolved in step 3. On a load nothing is selected yet, so this does what `clearIsSelected()`/`setIsSelected(..., false)` do there today.
2. **Hidden elements.** Drop the MPIDs that no longer exist from the hide controller's `_hiddenElementMPIDs` and `_hiddenScrapMPIDs`.
3. **Active scrap.** Keep it if it still names a scrap, otherwise use the first scrap (the same rule as the file-level row of §3.3). If no scrap remains, explicitly reset `_activeScrapID` to `0`; leaving it untouched would retain a removed scrap's ID on an existing controller. Resolve the active scrap before calling `resetSelectableElements()` and `updateSelectableEndAndControlPoints()`, then call `updateHasMultipleScraps()`. This refresh preserves the retained selection rather than using the selection-clearing mode transition in `setActiveScrap`. Apply, undo and redo all follow this rule, including replacement with an empty model.
4. **Snap targets.** With `initialSetup`, and when the file has a scrap, set the load defaults (`setSnapTargets(point, linePoint, [shot])`, today `:833-837`). Then `updateSnapTargets()` recomputes the targets from the model in every case, keeping the snap choices the user made.
5. **Station cache.** Without `initialSetup`, mark the Therion station cache dirty (`_markTherionStationPointNameCoordinateCacheDirty`), since any point may have changed.
6. **Used types.** Only with `initialSetup`, run `initializeUsedTypes()`. It counts every type again each time it runs (§2.5), so an undo or redo must not run it. Types that only a text apply introduces are counted when the user next uses them, as for any other element.
7. `updateEnableSelectButton()`, `triggerAllElementsRedraw()`, and finally `bumpStructureRevision()`, so the element tree rebuilds from the refreshed state.

A valid load calls it with `initialSetup: true` from `_finalFilePreparations`, which keeps only `_initializeReactions()`, `setFilename` and `_isLoading` (§2.5). The method now runs after the reactions are installed. Most reactions are autoruns, which re-run whenever their inputs change, so they end in the same state either way. The dirty-mirroring one is a `reaction` on `enableSaveButton` (`:1032-1033`), which fires only when the value changes. The refresh executes no command and doesn't touch `_hasUnsavedBaseline`, so it leaves that value false on a load and fires nothing. The existing load tests check this.

**Identity matching.** Before taking the `after` snapshot, `TH2TextIdentityMatcher` (new, pure, `lib/src/auxiliary/th2_text_identity_matcher.dart`) matches unchanged elements of the live and the detached model by content. Each element's **key** is its type and the text of its own lines without their endings (§4.2). The live side reads them from the session's writer line map, which describes `initialContent`, the live model's text (§4.6, _An apply that stays in text mode_); the detached side from the writer map of *N(T)*. A live and a detached element match only when they have the same key and that key is **unique on both sides** among the candidates of the pass. Order and position never break a tie, so duplicate elements with identical own lines are never paired arbitrarily. The passes are each linear in the number of elements:

1. **Within matched parents.** Starting from the file, which keeps its MPID (§4.5), group each matched parent's unmatched children by key on both sides, and match the keys that are unique on both. Recurse into the newly matched children. This resolves text repeated in different parents, such as the same coordinates in two lines, or `endline`.
2. **Across the file.** Among all elements still unmatched, match the keys that are unique on both sides. This keeps the identity of elements whose parent's own lines changed, and of elements moved to another parent, for example a point cut and pasted into another scrap.
3. **Containers through their children.** A scrap, line or area whose own lines changed has no key match, for example after an option edit on its header line, the main case of #38. An unmatched live container and an unmatched detached container of the same type match when they have at least one matched child, every matched child of the live one is matched to a child of the detached one, and the reverse. This runs from the deepest containers up (lines and areas, then scraps), so a scrap can be matched through lines that were themselves matched this way. Pass 1 then runs again inside each container matched here, for its children that are duplicated elsewhere in the file.

Elements left unmatched keep their detached MPIDs. Remap every MPID reference in the detached model consistently (element-map keys, parent and child MPIDs, option owners and other element references), then rebuild the thID and derived registries. Assert that serialization still equals the target normalized text. So selection, hidden state and expanded scraps survive for every element that can be told apart from its duplicates, including a scrap or line whose header the user edited. If identical own lines make a match ambiguous, those elements may get new MPIDs during an apply.

Every successful apply of a valid file uses this command once. Its `before` snapshot is a valid live model, so undo safely restores it before any older canvas command can run.

**Broken-file baseline.** The first apply of a broken file (§3.7) doesn't use this command:

1. Once the text parses cleanly, `TH2File.replaceContentsFrom(TH2File.fromMap(detached.toMap()))` puts a fresh copy of the detached model in place directly, with no command. `_isBroken` and `_problems` are cleared.
2. `undoRedoController.clearUndoRedoStack()` (`mp_undo_redo_controller.dart:110`) then runs, as `_actualSave` does. Nothing below this point can be undone, so the partial model is gone for good. Nothing else is lost: the stack is already empty. A broken file starts with an empty stack, and its tab shows the broken-file body instead of the canvas, so no canvas command can run. The element tree's moves and drawing-order actions also refuse a broken file (`th2_file_edit_element_edit_controller.dart:1397`, `:1462`).
3. **Canvas setup.** A broken load skipped the canvas setup in `_finalFilePreparations` (§2.5), so it runs now: the broken apply calls `syncControllersWithModel(initialSetup: true)` after step 2. That sets the active scrap, the default snap targets and the used types for the first time, as a valid load does. It doesn't run `_initializeReactions()` again: the broken load already installed the reactions (`:840`), and installing them twice would mirror the dirty state twice.
4. With an empty stack, `enableSaveButton` would be false, and the Save button, the dirty dot and Save All would treat the fixed file as saved. So the controller gains `@readonly bool _hasUnsavedBaseline`, which the broken apply sets. `enableSaveButton` becomes `!_isBroken && (_hasUndo || _hasUnsavedBaseline) && !_th2File.isNewFile`, and `hasUnsavedChanges` (§4.8) follows. `_actualSave` and a reload clear the flag. The flag also means "the file on disk is still broken", so `loadedBrokenProjectTH2FilePaths()` (§2.5) lists a controller when `isBroken || hasUnsavedBaseline`. Otherwise, once a fix is applied but not saved, _Run Therion_ would stop warning about the file, although Therion still reads the broken file from disk. After the fix is saved, the warning leaves it out. The broken-file help bullet on running Therion (§5, Phase 6) says that an unsaved fix still counts.
5. The way back is the existing paths. Before the apply, _Discard text changes_ (§3.1) returns to the broken-file body with the model untouched. After the apply, Reload (`MPGeneralController.reloadTH2File`, on the project tree's context menu and on the broken-file body) reads the file from disk again. The broken state then comes back from the file itself, not from a stored partial model. Reload doesn't ask before it drops an unsaved fix, as it doesn't for any edited file today (§2.5). Until it is saved, the fix shows as unsaved (item 4), so the dirty dot and the Save button make that visible.
6. Canvas edits and later text sessions stack up above the baseline as usual. Undoing all of them stops at the fixed text.

**Rejected alternative:** making the broken apply an undoable command that sets `_isBroken`/`_problems` back on undo. A canvas `Ctrl+Z` would then swap the canvas for the broken-file body, and redo would have to run from a screen with no canvas key handling. The command would own controller state outside the model. And it would give nothing useful: the disk file already holds the broken state.

**Rejected alternative:** reusing Reload (`MPGeneralController.reloadTH2File`) to build a new controller from the text. It throws away the undo history and all per-controller view state (zoom, active scrap, overlays), and the text edits could not be undone.

### 4.8 Dirty state and saving

- `TH2FileEditController` gains `@computed bool hasUnsavedChanges => enableSaveButton || (_textEditController?.isDirty ?? false)`. The text controller is kept after leaving text mode (§4.1), but `isDirty` is false outside a session (§4.6, _Ending a text session_), so text edits count as unsaved only while a session is open: on the canvas, `hasUnsavedChanges` equals `enableSaveButton`.
- `hasUnsavedChanges` replaces `enableSaveButton` as the **dirty** signal in `shouldKeepTablessTH2Controller`, which already returns `false` for a new file by its name. `enableSaveButton` keeps its current meaning, "the model has unsaved changes".
- **Save's enabled state** is a new `@computed bool canSave => hasUnsavedChanges && !_th2File.isNewFile`. It also replaces `enableSaveButton` in the dirty-mirroring reaction (`:1031-1047`) and in `_saveTH2ProjectFile`'s "already saved" check (`th_project_controller.dart:1574`). `hasUnsavedChanges` can't be used there: `enableSaveButton` is always false for a new file, but `isDirty` isn't, so text edits in a new file would add its placeholder path (`mpNewFilePrefix`) to `dirtyFilePaths`. `saveAllModifiedFiles` would then call `saveTH2File()` on it and get `saveFailed`, and `THProjectController.hasUnsavedChanges` would report the placeholder as unsaved until Save As. With `canSave`, a new file never enters `dirtyFilePaths`, as today, whether it was edited on the canvas or as text. It replaces `enableSaveButton` at every place that enables or runs Save (§2.2): the app bar's Save button, the overflow menu's Save item and `_saveActiveTab`. In TH2 text mode, it also enables the text view's toolbar Save button (§2.1), through `THTextEditorBuffer.canSave` (§4.9), instead of `isDirty`. So the toolbar button is disabled in a new file, and enabled when only the model has unsaved changes, as the app bar's button is. The canvas handler's whole `keyS` case (`mp_th2_file_edit_state_key_down_mixin.dart:178-188`) is **removed**, for both `Ctrl+S` and `Ctrl+Shift+S`. The page-level shortcuts (§2.2) are then the only keyboard path to Save and Save As on the canvas, so each runs once. That matters once `saveTH2File()` is asynchronous (below): the page's check could otherwise see the changes still unsaved while the canvas handler's save is pending, and save a second time. Save As is thereby **out of the Save gate**: its shortcut runs whatever the dirty or new-file state, and doesn't depend on `canSave`. The `!isNewFile` term keeps today's rule that **Save is disabled for a new file** (§2.2), which only Save As can write. Without it, text edits in a new file would enable Save, and `saveTH2File()` would write to the placeholder name.
- **`isNewFile` becomes observable.** `canSave` and `enableSaveButton` read `_th2File.isNewFile`, a plain field today (§2.5), which MobX doesn't track: `canSave`, a `@computed`, would keep a cached value when it changes, and the dirty-mirroring reaction wouldn't re-run. `TH2File` therefore keeps the flag in a MobX `Observable<bool>`, as `TH2FileEditSelectionController` does for `_selectionWindowCanvasRect` (`th2_file_edit_selection_controller.dart:119`), behind the same `isNewFile` getter and a setter that writes inside `runInAction`, so the callers (§2.5, `mp_general_controller.dart:548`, `mp_command_factory.dart:865`, `mp_sketch_option_widget.dart:232`) don't change. `toMap()`, `fromMap()` and `replaceContentsFrom` don't carry the flag (§4.7), so it stays a property of the live file. Every change of `isNewFile` now re-evaluates `canSave` and can fire the reaction, which is why Save As orders it after the commit and the new text session (below).
- The text editor's own `Ctrl+S` (`th_text_editor_widget.dart:489-492`) and toolbar Save button both call `_handleSaveIntent`, and so `TH2TextEditController.save`. That method checks the owner's `canSave` first and returns without doing anything when it is false, so in a new file `Ctrl+S` in text mode does nothing and reports nothing, as on the canvas, where `_saveActiveTab` checks `canSave`; `Ctrl+Shift+S` (page level) opens Save As. `saveTH2File()` also keeps a guard of its own for callers that skip `canSave`: on a new file, it returns `saveFailed` (below) without applying or writing.
- `saveTH2File()` becomes asynchronous and returns `Future<TH2FileSaveStatus>`, the enum the project save already uses (`th_text_file_save_result.dart:83`), instead of a new type. The enum gains `textHasProblems` (the apply was rejected) and `cancelled` (the apply was cancelled: the tab was closed or reloaded, or the text session was replaced). Its doc comment, which says the TH2 path has a single `saveFailed`, is updated. `saveTH2File()` returns `saved` after a write, `textHasProblems` or `cancelled` from the apply, and `saveFailed` for a new file (the guard above) and for a broken file with no text session. A failed write keeps throwing, as today. `alreadySaved`, `projectChanged` and `noOpenEditor` stay project-level: only `_saveTH2ProjectFile` returns them. `cancelled` isn't an error: callers report nothing for it. In text mode, `saveTH2File()` passes `lockBufferOnAccept: true` and awaits the apply result before writing, so `rejected` and `cancelled` never reach the write. Its operation-owned lock remains held through the write, commit and session replacement, and is released with the operation gate in an inner `finally`, including write and regeneration failures (§4.6). A stale validation result is retried against the current buffer (§4.6). The apply runs **before** the existing `if (_isBroken) return;` guard at the top of `saveTH2File()` (`:1660`). For a broken file, a successful apply clears `_isBroken` and sets `_hasUnsavedBaseline` (§4.7), so the guard then lets the save through. Outside text mode, the guard is unchanged, so a broken file with no text session still can't be saved. `_saveTH2ProjectFile` awaits `saveTH2File()` and passes its status through, including `textHasProblems` and `cancelled`; it must not remove the dirty path or report `saved` before the awaited write succeeds. Most UI callers have no error path today (§2.2), and once `saveTH2File()` is asynchronous an exception from an unawaited call becomes an unhandled future error. So every UI path to Save runs through `_saveActiveTab`, which already awaits inside a `try/catch` and logs the failure: the app bar's Save button, the overflow menu's Save action and the page's `Ctrl+S`, the last as today. Save As gets the same treatment: `_saveActiveTabAs` becomes asynchronous, awaits `saveAsTH2File()` inside a `try/catch` that logs the same way, and the app bar's Save As button and the overflow menu's Save As action call it instead of `saveAsTH2File()`. `TH2TextEditController.save()` (§4.9) uses the same logging. `_saveTH2ProjectFile` keeps its own `try/catch`.
- **Save As in text mode** first **validates** the current buffer (§4.6), before the file picker opens. Validation is a detached parse, usually already cached, and doesn't change the model. When the text doesn't parse, Save As is refused in the same way as Save, and no picker opens. The text is **applied only after the picker returns a path**, with `lockBufferOnAccept: true`, before anything else that path triggers: the `.th2` extension rename, `renameFileController`, the filename change and the image-path rebasing. A dismissed picker therefore changes nothing: no apply, no canvas undo step, and the text session and its `TextField` history are kept. The picker may not block the Mapiah window, so the buffer can change while it is open. Save As therefore **holds the tab's operation gate** (§4.6) from the validation before the picker until after the write and the new text session. While the picker is open, `F2`, the _Canvas_ button, Save, a second Save As and gated tree edits wait for it, and tree clicks are ignored (§4.14). Otherwise a leave could apply the text and end the session during the picker, and the apply after it would return `cancelled` although the user had chosen a name. Typing isn't gated, and the apply's snapshot check (§4.6) then validates the current buffer again, and if that text no longer parses, Save As returns `textHasProblems` and writes nothing. The `if (_isBroken) return;` guard at the top of `saveAsTH2File()` (`:1672-1675`) is skipped in text mode, where validation decides: a broken file whose text validates gets through to the picker, and the apply after the picker clears `_isBroken` (§4.7). Outside text mode, the guard is unchanged. The app bar's Save As button and the overflow menu's Save As item, both disabled today for a broken file (§2.2), are enabled for a broken file in text mode. `saveAsTH2File()` returns `Future<TH2FileSaveStatus>` too: `cancelled` when the file picker is dismissed or the apply is cancelled, `textHasProblems` when the apply is rejected. All Save As callers await or explicitly handle it, including the page-level shortcut, the only keyboard path to it (above); they do not treat a pending picker or write as a completed save.
- **Commit save state after the write.** `_actualSave` first serializes and encodes the model, then writes and flushes the bytes. Only after `writeAsBytesSync` succeeds does it clear the undo/redo stack, update undo/redo status and clear `_hasUnsavedBaseline`. The callers likewise set `isNewFile = false` only after the write succeeds. If encoding or writing throws, the applied model, its undo history, `_hasUnsavedBaseline` and the dirty path remain available for retry; the failure reaches the caller's `try/catch` (§4.8, above). When the save applied the text, the tab gets a new text session from the applied model even after a failed write (§4.6). Its `initialContent` is the applied model's text, so a retry has nothing to apply and adds no second canvas command. Save As may need the target filename and rebased image paths to serialize the target bytes, but it must commit the controller rename only after a successful write and roll back any pre-write model changes on failure. `_actualSave` is therefore split into the write and the commit, and Save As runs, in this order: the apply (text mode), the filename and image-path changes, the write, `renameFileController`, the commit (undo/redo stack, undo/redo status, `_hasUnsavedBaseline`), in text mode the new text session (§4.6), and only then `isNewFile = false` and `_markLoadedAfterSaveAs()`. The dirty-mirroring reaction watches `canSave` and uses `_th2File.filename`, which already names the new path once the write starts. It removes the mark when `canSave` turns false: at the commit, unless the old session's buffer is still dirty (an edited buffer, applied or normalizing back to its initial text), which keeps `canSave` true until the new text session, since the apply doesn't end the session (§4.6). So the rename must come before both: it moves the dirty mark to the new path (§2.5), and `canSave` turning false then removes it from there. With the commit or the new session first, the reaction would remove the new path, which isn't marked, and the rename would then move the old path's mark to the new one, so the saved file would show as unsaved: the bug that `07d83627` fixed. `isNewFile = false` must come after the commit and the new session, now that it is observable (above): before them, in a new file, `canSave` would turn true while undo steps or the old session's dirty buffer remain, and the reaction would add the new path. A failed write leaves the controller registered, and the mark, under the original path. On failure, the new text session is started after that rollback, so it shows the original image paths. `_saveTH2ProjectFile` removes the dirty path only after the awaited result is `saved`.

### 4.9 Editor widget reuse

- Extract `THTextEditorBuffer`, an abstract class with the members listed in §2.1, plus `List<THTextEditorDiagnostic> get diagnostics` and `THTextEditorLanguage get language`. `THTextEditorController` and the new `TH2TextEditController` implement it. `THTextEditorWidget` takes `THTextEditorBuffer`.
  - **Save.** The two controllers' saves return different types: `Future<THTextFileSaveResult>` and `Future<TH2FileSaveStatus>` (§4.8). The widget ignores the result (§2.1), so the interface declares `Future<void> save()`. `THTextEditorController` keeps its `Future<THTextFileSaveResult> save()`, a valid override, so its callers don't change. `TH2TextEditController.save()` returns `Future<void>`: it checks `canSave` (§4.8), awaits the owner's `saveTH2File()` and catches and logs a failure itself, as `_saveActiveTab` does (§4.8). Callers that need the status call `saveTH2File()`.
  - **`bool get canSave`** enables the toolbar's Save button. `THTextEditorController` returns `isDirty`, so `thconfig`/`.th` tabs don't change; `TH2TextEditController` returns its owner's `canSave` (§4.8).
  - **`bool get isReadOnly`** exposes the operation-owned buffer lock for Save, Save As and tree edits (§4.6, §4.8, §4.13); `THTextEditorController` returns `false`. The widget binds it to the `TextField` and disables buffer-mutating toolbar and find/replace actions. Controller mutation methods and custom shortcut handlers also check the lock, so programmatic replace, indentation and text undo/redo cannot bypass it. Internal session regeneration uses a separate path and remains allowed. Scrolling, selection, find and copy stay available.
  - **Revert.** `TH2TextEditController.revert` is _Discard text changes_ (§3.1). The toolbar shows it with the button's Revert icon and a TH2 tooltip, through a new `String? get revertTooltip` that is `null` for `thconfig`/`.th` tabs.
  - **`leadingToolbarActions`**, an optional widget list on `THTextEditorWidget`, shown at the start of its toolbar. TH2 text mode puts its _Canvas_ button there (§4.1).
- **Pending selection without focus.** `_applyPendingSelectionRange` always requests focus (§2.1). The buffer gains `bool get pendingSelectionRequestsFocus`, set together with `pendingSelectionRange` and cleared with it, `true` by default. The widget requests focus only when it is `true`. Multi-file search navigation keeps setting it to `true`; `moveTextCursorToElement(requestFocus: false)` sets it to `false` (§4.14).
- The find/replace state and logic move from `THTextEditorController` into a `THTextEditorFindMixin` used by both, so they behave the same.
- `THTextEditorDiagnostic` (line, message, severity) replaces the widget's direct use of `THProjectParseError`. `THTextEditorController` maps its project errors to it. `TH2TextEditController` maps `TH2FileProblem`s (with the localized category from `TH2FileProblemTextAux`), line-less parser errors, and normalization records (§4.12). Severity gains an `information` level, drawn with its own marker color, that never blocks an apply or a save.
- **One marker per line.** The widget draws one diagnostic per line (§2.1), and a line can now get both a problem and an information marker. So `_buildDiagnosticBackground` groups diagnostics by line instead of keeping the last one, and `THTextEditorDiagnosticMarkerWidget` takes the line's list. It uses the color of the most severe one (error, then warning, then information), and its tooltip lists them all, most severe first, so none is hidden.
- **Enter.** `THTextEditorBuffer` gains `String get lineEnding`. `THTextEditorController` returns `\n`; `TH2TextEditController` returns the file's default, `TH2File.lineEnding`. In TH2 mode, handle the actual newline-insertion action from Enter through a dedicated editor action, rather than inferring Enter from `_onTextEditingChanged`'s length/newline heuristic (§2.1). Bind Enter and Shift+Enter, each on the main keyboard and the numpad, including repeat events. A `SingleActivator` matches only its exact modifiers, so Shift+Enter needs its own binding: without it, the platform's text input would insert a bare `\n` with no auto-indent, and a CRLF file would get an LF line typed with Enter. Bind them while preserving platform IME composition handling: an Enter that confirms an active composition must not also insert a newline. The action replaces the selected range (or inserts at a collapsed cursor) with the file's default ending and computed auto-indent in one `TextEditingValue` update, with the cursor after both. `_computeAutoIndent` reads the preceding text without a trailing `\r`. The update enters the existing `TextField` undo history normally. Pasted text, including a single `\n`, and programmatic replacements bypass this action and keep their supplied endings without auto-indent; the TH2 listener no longer infers Enter from their resulting text changes. The `therion` editor retains its current behavior. The action observes `isReadOnly` (§4.13).
- `THTextEditorLanguage { therion, th2 }` chooses the tokenizer, the fold keywords and the auto-indent block openers (§2.1). For `th2`, the openers are `scrap`, `line`, `area` and `comment`, matching its folds (§4.10). `tokenizeTherionText(text, language:)` keeps its default, so current callers don't change.

### 4.10 TH2 highlighting and folding

- TH2 keywords: `encoding`, `scrap`, `endscrap`, `point`, `line`, `endline`, `area`, `endarea`, `comment`, `endcomment`. Option words that begin a line inside a `line` block (`smooth`, `subtype`, `orientation`, `l-size`, `size`, `mark`, `altitude`, `adjust`, `direction`, `gradient`, `height`, `border`, `reverse`, `visibility`, `place`, `clip`, `outline`, `close`, `id`) are colored as `option`.
- `##XTHERION##` and `##MAPIAH##` at the start of a line color the whole line as a new `THTextEditorTokenType.setting`, not as a comment.
- A `\r` at the end of a line, from a `\r\n` ending, is part of the ending: the TH2 tokenizer and fold builder ignore it, so a CRLF line is colored and folded like an LF line.
- The TH2 tokenizer carries state across lines: the lines between `comment` and `endcomment` are colored as `comment`.
- Folds: `scrap`/`endscrap`, `line`/`endline`, `area`/`endarea`, `comment`/`endcomment`.
- Token colors come from the existing editor palette. One new color token is added for `setting`, for light and dark themes.

### 4.11 Centering the canvas without zooming

`TH2FileEditController.revealSelection()` (new) checks the selection's bounding box, or the selected line point, against the visible canvas rectangle. If it isn't fully visible, it moves `_canvasCenterX/Y` to its center, reusing the math in `_setCanvasCenterOnZoom` (`:1601`) but keeping the scale. Like `requestZoomToFit`, it waits for layout when the canvas hasn't been laid out yet, because it runs right after the body widget swaps back to the canvas.

### 4.12 Parser normalization

Parsing a text *T* and writing the result back can give a different text (§2.3). Making the parser lossless was rejected: the clean-up passes keep the model valid (a line needs 2 points, an area needs a border), and they run on every file load, so changing them would change how existing files open. Rejecting text the parser would change was rejected too: it would turn harmless input, such as a duplicate point, into errors, although Mapiah accepts that input when loading a file. Instead, text mode accepts the parser's result and works on it:

- **Normalized text.** For the current text *T*, *N(T)* = `serializeWithLineMap` of its detached model, with the same options as §4.2, its line endings kept as they are. It is the text Save would write. The no-op and apply checks use *N(T)*, not *T* (§4.6).
- **Normalization records.** Each clean-up pass records what it did as a `TH2FileNormalization` (raw line, kind), next to `problems`. The kinds are `rewrittenLine` (`_cleanOriginalLinesInFile`, and `_resolveBorderReference` when it repairs a border reference, §2.3), `removedDuplicateLinePoint` and `removedShortLine` (`_linesCleanUp`), and `removedEmptyArea` (`_areasCleanUp`). Moved and added lines aren't records: they come from the comparison in the next item. Their line numbers come from the parser's start lines (§4.4); a removal record reads its line before the removed element's entry is dropped. Loading a file ignores the records, so loading behaves as today.
- **Other differences.** Some changes don't come from the clean-up passes. The writer adds an `encoding` line when the first line isn't one, writes a `##MAPIAH##` image line that XTherion can represent as a `##XTHERION##` line, and writes all settings together (§2.3). They are found through the detached model itself: *T* was parsed into it and *N(T)* was written from it, so the parser's map (§4.4) gives each element's lines in *T*, and the writer's map (§4.3) its lines in *N(T)*, under the same MPIDs. One pass over the surviving elements finds:
  - **Rewritten:** the element's own lines in *T* and in *N(T)* differ, compared without their endings (§4.2), and no record covers it. Each of its raw lines gets a generic "Mapiah will rewrite this line" marker.
  - **Moved:** taken in *T* order, the elements' first lines in *N(T)* should increase. The elements outside one longest increasing subsequence of those lines (found in O(n log n)) are the ones the writer relocated, like a setting typed away from the settings block. Each gets a "Mapiah will move this line to line X" marker, with X counted in *N(T)*. A moved element whose text also changed gets both markers, which §4.9 groups on its line.
  - **Added:** a line of *N(T)* whose owner has no lines in *T*, such as the synthesized `encoding` line, owned by the file. It gets a "Mapiah will add: …" marker on the raw line of the next element in *N(T)* order that has raw lines, or on the last raw line when there is none (line 0 for an empty buffer).
  - **Removed** lines (§4.4) get their record's marker and nothing else.

  In debug builds, a rewritten element whose detached copy still holds its stored source text (`originalLineInTH2File`) is logged, other than an image written in XTherion format (§2.3). The writer reproduces stored text exactly, so such a difference means a clean-up pass or writer path that changes text without recording it.
- **Markers.** Records and the differences above become `information` diagnostics (§4.9), with one localized message per kind. The user sees each rewrite at its line while editing, before leaving text mode, and nothing is blocked.
- **Cursor mapping.** A raw line of the final *T* is mapped through its owning element, to the line at the same offset among that element's *N(T)* lines, or to its last one when it has fewer. A removed line goes where the nearest raw line above it with a surviving owner goes, or to line 0 when there is none. No line is ever matched by text similarity. This is used after an apply (§4.6), whose identity remap keeps *N(T)* as the live model's text (§4.7), and after a save, when the editor shows *N(T)* (§3.6).

### 4.13 Tree edits in text mode

- **One scoped helper for gated tree edits.** `prepareTH2FileForTreeEdit` (§2.6) is replaced by `Future<T?> MPGeneralController.runTH2TreeEdit<T>(String th2FilePath, Future<T?> Function(TH2FileEditController controller) edit, {bool leaveTextMode = false})`. A gate that only returns a controller can't work here: the operation ends in the caller, after the edit, and each caller has its own early returns (stale MPIDs, a missing row, an invalid target). If one of them returned without starting the new text session (§4.6), the buffer would stay dirty against the old `initialContent`, and the next leave, Save or tree edit would run a second `MPReplaceTH2FileContentsCommand` whose `before` and `after` are the same model. The helper owns the whole operation instead:
  1. It runs today's checks (no loaded controller, a broken file, a load error) and returns `null` when one fails, then activates the tab, so the "can't apply" message shows on the right tab, and leaves creation modes on the canvas.
  2. It takes the tab's operation gate (§4.6) and holds it until step 5.
  3. In text mode, it awaits a new `TH2FileEditController.applyTextBeforeExternalEdit()`, which awaits `applyTextContent` with the current buffer (§4.6) and shows the "can't apply" message on `rejected`. On `rejected` or `cancelled`, it returns `null` without calling `edit`. It passes `lockBufferOnAccept: true` (§4.6), so on accepted validation, after checking that the buffer and session still match, `applyTextContent` synchronously locks buffer mutations before applying the text, also for an `unchanged` result and for a buffer equal to `initialContent`. The helper owns that lock independently of the text session until its `finally` completes, so ending or replacing the session does not release it; the lock does not cover the preceding awaited validation.
  4. Otherwise, it checks that the controller is still live and backs the same tab, then awaits `edit(controller)`. While it runs, `execute`'s new-session requests are deferred (§4.13, _Regenerating the text_).
  5. In a `finally`, so an early return or an exception inside `edit` is covered too, it ends the operation. It restores buffer mutability and releases the gate in an inner `finally`, even if session regeneration fails, and only after the session replacement or mode exit below has completed. A disposed controller is not given a new session. In text mode, it starts the one new text session of §4.6 when the apply result was `applied` or a command ran. With `leaveTextMode: true` and an `applied` or `unchanged` result, it instead ends the session and sets `editMode` to `canvas`, mapping the cursor from the apply result as a leave does, without calling `leaveTextMode()`: that would validate the old session's buffer against its pre-apply `initialContent` and apply a second time.

### 4.14 Tree clicks in text mode

- **Branch in `_onTap`.** `_onTap` (§2.6) checks `controller.editMode` after `_validControllerFor`. In text mode, it resets the tap tracker, brings the tab to the front as today, and calls a new `TH2FileEditController.moveTextCursorToElement(int mpID, {bool requestFocus = true})` with the row's element or scrap MPID. It then returns, skipping the Ctrl, Shift and double-tap branches, `_leaveCreationMode` and `_applyDoubleTapExtras`. So no selection changes and no zoom request is queued for the hidden canvas.
- **Branch in `_onBeforeOpenMenu`.** `_onBeforeOpenMenu` (§2.6) checks `controller.editMode` the same way. In text mode, it calls `moveTextCursorToElement` with the row's element or scrap MPID and returns, skipping `_leaveCreationMode` and the selection change. It passes `requestFocus: false`, because the menu that is opening takes the focus. The shared menu wrapper, `THProjectTreeRowContextMenuWidget` (`th_project_tree_row_context_menu_widget.dart`), calls `onBeforeOpen` from its secondary tap (`:115`) and builds a `MenuAnchor` with no `onClose`. It gains an optional `onAfterClose`, passed to `MenuAnchor.onClose`. The TH2 row uses it to request focus on `textEditorFocusNode` when the tab is still in text mode, so the user can type once the menu closes. On the canvas, a scrap row's `_onBeforeOpenMenu` still does nothing.
- **Line lookup.** `moveTextCursorToElement` does nothing while an apply or other gated operation is pending (§4.6). Otherwise it reads the element's first own line from the current text session's writer line map, which describes `initialContent` (§4.2, §4.3). If the buffer equals `initialContent`, that line is used. If not, the session's line tracker (below) takes it to the current buffer. If the element's first line was edited or deleted, it goes to the nearest unedited line above, or line 0 when there is none. An MPID missing from the line map does nothing.
- **Line tracker.** `TH2TextLineTracker` (new, pure, `lib/src/auxiliary/th2_text_line_tracker.dart`) follows the lines of `initialContent` through the buffer's changes. Each new text session starts with an empty one. On each buffer change, `TH2TextEditController.setContent` finds the replaced range by trimming the common start and end of the old and new text, and records it as a line-range replacement: old lines *a* to *b* replaced by *k* lines. An insertion exactly at a line's start only shifts that line; any other change marks the lines it touches as edited. Lines are counted at `\r\n` and `\n` (§4.2). Text undo and redo, indentation, paste and Replace are changes like any other, and Replace All is one change from its first to its last match. A line they touched stays edited, even after an undo restores it: conservative, but never a wrong line. A lookup replays the recorded replacements on the one line asked for, so its cost grows with the number of changes in the session, and a change costs only the trim. It works on text that doesn't parse, which a lookup through a parse could not.
- **Cursor and focus.** The line is set through `pendingScrollToLine`, and the cursor is put at its first non-blank column through `pendingSelectionRange`, as on text-mode entry (§3.2). `requestFocus` is passed on as `pendingSelectionRequestsFocus` (§4.9). The widget applies the pending selection in its next build, and with `requestFocus: true` it requests focus on `textEditorFocusNode` then, as it does today. With `requestFocus: false` it doesn't: the context menu opens in a post-frame callback (`th_project_tree_row_context_menu_widget.dart:131-137`), and focusing the text field in that same frame would take the focus away from the menu.
- The tree reflects the live model, and that model is the source of `initialContent`, since any command run in text mode, and any apply that keeps the tab in text mode, starts a new session (§4.6, §4.13). So every element row the tree shows has an entry in the session's line map. A broken file's session has no writer line map (§3.4), but `_validControllerFor` (`th2_element_tree_row_widget.dart:119-131`) already ignores clicks on a broken file's rows.

## 6. Risks and Open Questions

1. **Coarser canvas undo.** All edits in one text session become one canvas step. Users can still undo typing within text mode using the existing `TextField` history. Separate applies create separate canvas steps.
2. **Identity matching.** A whole-file apply can keep clearly matched unchanged MPIDs, but identical repeated elements may be ambiguous. Those elements can receive new MPIDs, which may reset their selection or hidden state. Content-keyed matching (§4.7) keeps the rest, including containers whose header changed. `t3965` and `t3967` cover this.
3. **Idle parsing cost.** Large files may make current-buffer validation noticeable. Debounce it, ignore stale results, and measure cached and uncached apply in `t3971`. The comparisons around the parse are linear or near-linear (§4.6), so the parse itself is the cost to watch.
4. **Snapshot size.** Each canvas apply stores two deep file snapshots. `t3971` measures the cost on a large fixture.
5. **No unsaved-changes guard.** Unsaved text edits are lost without a prompt when the tab is closed, the app quits or the file is reloaded, as canvas edits are today (§2.5). An app-wide guard for tab close, quit, Reload and project switch, covering every file type, is left to a separate issue. It can use this plan's `hasUnsavedChanges`, which already counts text edits and an unsaved broken-file fix (§4.7, §4.8).
