## 1. Purpose and boundaries

Let the user fix a broken `.th2` file in text mode. The broken-file body gets _Edit as text_, and `F2` works there too. Both open a **raw session**: the file's text as it is on disk, decoded with the file's encoding, with the parser's problems marked on their lines. Once the text parses cleanly, the first apply installs it as a **new baseline**, not an undo step. That apply clears the broken state and the undo stack and runs the canvas setup that a valid load runs. The file then counts as unsaved until it is saved. After that, the file behaves like any valid file.

This phase also covers the broken-file items that Phase 4 moved here (Phase 4 plan, §3 change 8): `F2` on the broken-file body, Save As for a broken file in text mode, and the broken-file cases of `t3980`, `t3984`, `t3987`, `t3988` and `t3990`.

Do not create a Phase 5 branch and do not merge into `main`. The branch merges after Phase 6 at the earliest (parent §5, _Branch and merge_). The main checkout stays on `main`.

Out of scope: help pages, keyboard shortcut pages, CHANGELOG and the final review of the strings (Phase 6), and the native undo first-snapshot delay (Phase 7).

## 3. Scope and changes to the parent plan

### In scope

Everything in the parent's Phase 5 entry (§5), including the items Phase 4 moved there.

### Changes to the parent plan

Record these in the parent's Phase 5 entry, and in the sections they change, when this plan is implemented (§5 step 4):

1. **Leaving an unchanged raw session returns to the broken-file body, unless that text validates.** The parent covers Discard, but not a leave (`F2`, _Canvas_) with an unchanged buffer. The leave validates that buffer through the session's cache, which holds the entry's result (change 2), so it normally doesn't parse. When it is invalid, applying it could only be rejected, and showing the "can't apply" banner for text the user never touched would be noise, so the leave does what Discard does. This holds whatever the buffer went through: a buffer edited and undone back to its initial text leaves the same way, whether or not idle validation ran in between. When it is valid, because the file was fixed outside Mapiah after the load (§2, _Raw text source in practice_), the leave applies it as any edited raw buffer is applied, so the user isn't stuck on the broken-file body with Save disabled (§4.4).
2. **The raw session opens with its problems marked.** The parent says the problems are shown as line markers. Here the entry validates the raw source before it installs the session, and installs it with that validation cache (§4.2, §4.3), instead of converting `TH2FileProblem`s. The markers are then exactly the diagnostics an apply would give, and they show with the editor. The cursor starts on the first error's line from that validation, not from the load's problems, so it stays right when the file changed on disk after the load.
3. **Save As in a raw session always validates before the file picker.** Phase 4 treats a buffer equal to `initialContent` as valid without a parse. For a raw session that buffer is broken text. Without this change, the picker would open, empty the picked file (Phase 4 plan, §2), and only then would the apply reject the text. Unlike a leave (change 1), a Save As of broken text the user never touched shows the "can't apply" banner: Save As is an explicit request to write the text, and the banner tells why it didn't happen, while a leave of untouched text only asks to get out of text mode.
4. **Unreadable raw text refuses entry with a message.** The parent assumes the disk text can always be decoded. A file that is no longer readable, or isn't valid in its encoding (invalid UTF-8 loads as broken, §2), can't be edited as text. Entry shows a localized message and keeps the broken-file body (§4.2). The cases get different messages. A read failure says Mapiah can't read the file. A decoding failure in a known encoding names the encoding and says what to do: convert the file to that encoding, or set its `encoding` line to the encoding it uses, in another editor, then reload. Decoding fails in two ways. UTF-8 and ASCII fail on any byte they can't decode. UTF-8 is also used with no `encoding` line and for an encoding name Mapiah doesn't know (`MPEncodingAux.decode` falls back to it, and the `encoding` line accepts any name). The single-byte code pages of the `charset` package fail on a byte the page doesn't define (`FormatException("Not defined in this code page")`), such as 0x81 in CP1252 or the holes of ISO8859-3, -6, -7, -8 and -11. When the name is unknown, the message can't tell the user to convert the file to it: a third message says that Mapiah doesn't know the encoding, so it read the file as UTF-8, and asks for an `encoding` line naming the encoding the file uses (§4.1, §4.2). The typical file declares UTF-8 or nothing but was written in cp1252 or Latin-1. Rescuing such files inside Mapiah is left to a separate issue: Latin-1 fallback would silently garble a UTF-8 file with one bad byte, and a lenient UTF-8 decode needs diagnostics the text-only validator can't give (§7 risk 6).
5. **The broken-file body holds the canvas focus node and requests focus when it mounts.** Without a focused node inside the tab, tab activation focuses nothing, and the focus stays wherever it was, possibly in another tab. The body wraps its content in a `Focus` with `th2FileFocusNode`, the node the canvas's `MPListenerWidget` uses. Tab activation requests focus after the frame, often while the load is still pending and the body isn't mounted, so the request alone would leave a freshly opened broken tab unfocused. `autofocus` doesn't cover that: Flutter applies an autofocus only while the enclosing scope has no focused child, and the page's own `Focus(autofocus: true)` (`th2_file_tabs_page.dart:1142`), or another tab's node, normally has focus. So the body requests focus explicitly once it mounts, if its tab is the active one (§4.2). Sharing the node is safe because the canvas, which also uses it, is never mounted together with the body.
6. **A raw session has an unowned line map.** The parent doesn't say which map describes the raw text. No element of the broken model reliably owns a line of it, so the map has no owners (§4.3). Tree navigation, Copy and canvas history traversal then do nothing in a raw session, which matches the tree: it shows no element rows for a broken file.
7. **Strings arrive with the code**, as in Phase 4 (its §3 change 4): _Edit as text_, its tooltip, the unreadable-text and the two encoding messages, and the broken-file body's explanation, which today says Mapiah can't edit or save the file (§4.7). Phase 6 reviews them.
8. **A Save As collision restores a broken file from its loaded bytes.** Phase 4's collision handling (Phase 4 plan, §3 change 11) treats another controller with unsaved changes as already marked dirty: its own Save writes the file again. A broken controller with an edited raw session now has unsaved changes, but its Save writes nothing until the text is valid, and Discard drops the only copy left, since the picker emptied the file. Phase 4 can't restore a broken file either: its model can't be written reliably, so it gets the "emptied" message. Left that way, a later _Edit as text_ on that tab would read the emptied file (§4.1), whose empty text probably validates, so leaving with it unchanged would install an empty baseline, while the body still lists the old problems. Instead, a broken controller keeps the bytes its load parsed (§4.1), and the collision writes them back, with or without a raw session, edited or not, so the file holds what it held at the load, and the user gets the "open in another tab" message (§4.6). Only a failed restore gets the "emptied" message. The "already marked dirty" branch never applies to a broken controller.
9. **The _Running Therion_ help covers Save As.** The parent's Phase 6 help bullet says an unsaved fix still counts as broken. It also needs to say that the warning only covers loaded files, so after a Save As of a fix to a new name, the original file, still broken on disk, can break the Therion run without a warning (§7 risk 5).
10. **Reload stays reachable after an unsaved fix.** Parent §4.7 step 5 says Reload is on the project tree's context menu after the apply, but that menu offers it only for a broken or failed controller (§2, _Reload_), and the broken-file body is gone once the canvas shows. The menu also offers Reload, after the valid file's own entries, while `hasUnsavedBaseline` is true, so the way back to the broken state stays in the UI until the fix is saved (§4.7).
11. **The _Run Therion_ warning says "broken on disk" and marks an unsaved fix.** Parent §4.7 step 4 lists a controller with an unsaved fix as broken, but the dialog's text says the loaded file "is broken", which contradicts its working canvas. The heading says "on disk", and such an entry gets a "(fix not saved)" suffix (§4.7). The project tree's broken badge still leaves with the problems. The Phase 6 _Running Therion_ help bullet mentions the suffix (with change 9).
12. **The text view's leave button says "Leave text mode" while the file is broken.** Its tooltip, "Canvas (F2)", promises a canvas that a raw session reaches only when its text fixes the file. With broken text it leads to the banner or back to the broken-file body. While the file is broken, the tooltip is "Leave text mode (F2)"; the icon doesn't change (§4.4). The Phase 6 help says in one sentence what leaving a broken file's text mode does.
13. **`t3940` changes beyond the new button.** The parent's Phase 5 entry says `t3940` is "updated only for the new _Edit as text_ button". It also changes for the new `th2BrokenFileExplanation`, the rename of "a broken file is never dirty and Save As is disabled", since an edited raw session makes a broken file dirty, the Save As assertion in a raw session and the new buttons case (§6).

## 4. Design

### 4.1 The raw text source

`TH2FileParser` gains `static String decodeSourceBytes(Uint8List bytes)`. It runs `detectEncodingFromBytes(bytes).encoding`, then the same decoding as `_decodeFile`, which it shares (`MPEncodingAux.decode`, then `_stripNul`). The byte path of `parse` uses the shared code, so the raw buffer is exactly the text the load parsed, and the problem lines match. When decoding throws a `FormatException`, it throws `TH2SourceDecodingException` (new, in `th2_file_parser.dart`) instead, with `encoding`, the detected Therion encoding name, `isKnownEncoding`, whether `MPEncodingAux.encodingByTherionName(encoding)` isn't `null` (when it is `null`, `decode` used UTF-8), and `cause`, the original exception. Every decoder a Therion name can reach throws a `FormatException` on bad input: Dart's `utf8` and `ascii`, and the `charset` package's code pages (§3 change 4). The load's `catch (e)` in `parse` (`:3225-3228`) catches it as it caught the `FormatException`, so a load records it as before, with the new exception's `toString()`, which includes the cause's.

`TH2FileEditController._readBrokenFileSource()` (new, async) takes `_th2File.fileBytes` when it is set, otherwise `await File(_th2File.filename).readAsBytes()`, and returns `TH2FileParser.decodeSourceBytes(bytes)`. The bytes are those on disk, not a write of the model. This means an encoding change made through Properties on the broken-file body has no effect on the raw text (parent §4.7, baseline step 2).

**Loaded bytes of a broken file.** `_loadOnce` reads the bytes itself before the parse: `_th2File.fileBytes` when it is set, otherwise `await File(_th2File.filename).readAsBytes()`. It passes them to `parse(fileBytes: …)`, so the parser doesn't read the file again. When the read throws, it passes `null`, and the parser meets the same failure and records it as a broken load, as today. `_commitLoadResult` keeps the bytes in a new private `Uint8List? _brokenSourceBytes` only when the load is broken (`loadedIsBroken`), and `null` otherwise, so a valid file holds no extra copy. The field isn't observable: only the Save As collision reads it (§4.6). The baseline clears it (§4.5), and a reload replaces the controller, whose new load sets it again. It describes the load, not the disk: entry still reads the disk (`_readBrokenFileSource`), so a file fixed outside Mapiah after the load still opens fixed. Keeping the bytes costs one copy of each broken file in memory, and broken files are rare and small.

### 4.2 Entering a raw session

**_Edit as text_.** `TH2BrokenFileBodyWidget` gets an `ElevatedButton` (key `TH2BrokenFileBodyEditAsTextButton`), labeled _Edit as text_, inside a `Tooltip` with "Edit as text (F2)". It calls `controller.requestEnterTextMode()`. Today the body's `Column` ends with the Reload `ElevatedButton`, shown only when `onReload != null`. The two buttons go into one `Wrap`, which replaces that last child: _Edit as text_ first, then Reload when `onReload != null`, with `spacing` and `runSpacing` from a new `mpTH2BrokenFileBodyButtonSpacing` (8) in `mp_constants.dart`. _Edit as text_ doesn't depend on `onReload`: it is shown whenever the body is, also where the body has no Reload. The `Wrap` lets the buttons go onto a second row in a narrow tab.

**Feedback while the entry runs.** Entry parses the file before the editor shows (step 4 below), so a large file pauses after the press. The gate drops a second press or `F2` silently, so without feedback the button seems to do nothing. _Edit as text_ is therefore an `ElevatedButton.icon` inside its own `Observer`, which reads the existing observable `controller.isOperationBusy` (`th2_file_edit_controller.dart:88`). The body widget itself stays a `StatelessWidget` that observes nothing. While busy, `onPressed` is `null` and the icon is a `CircularProgressIndicator` of `mpTH2BrokenFileBodyEditAsTextProgressSize` (16, new in `mp_constants.dart`) with `strokeWidth` 2. Otherwise the icon is `Icons.edit_note`. The label doesn't change. On the broken-file body, only the entry keeps the gate busy: Save As with no session returns at once, and Properties isn't gated. So busy means "opening as text" there, and `F2` gets the same feedback, since it runs the same entry under the same gate. The spinner shows with no delay. For a small file, the editor replaces the whole body within a frame or two, so the spinner is never visibly drawn, and a delay would only add a timer and widget state. Showing the editor read-only before the parse was rejected: it would install a session before its validation and place the cursor before the first error is known, which step 4 avoids.

**Focus.** The body's `SingleChildScrollView` is wrapped in a new private `_TH2BrokenFileBodyFocusWidget` (a `StatefulWidget` in `th2_broken_file_body_widget.dart`, taking the controller and the child). It builds `Focus(focusNode: controller.th2FileFocusNode, child: child)`, the node the canvas's `MPListenerWidget` attaches (`mp_listener_widget.dart:198-200`), with no `autofocus`. Tab activation, Discard and the post-frame focus of Phase 4 (`activeFocusNode`) then land in the broken body, and `F2` bubbles from there to the page's binding.

Its `initState` adds a post-frame callback that requests focus on `th2FileFocusNode` when the widget is still `mounted`, the controller isn't disposed, `editMode` is `canvas`, `isBroken` is true, and the controller's file is the active tab (`mpGeneralController.openFileOrder[activeTabIndex] == controller.filename`, with the index checked against the list's bounds). It schedules a frame, as `_focusActiveNodeAfterFrame` does. This covers the first show of a freshly opened broken tab: tab activation requests focus after the frame (`th2_file_tabs_page.dart:124-133`), usually while the load is still pending, so that request finds the node unattached, and the body mounts only when the load completes. `autofocus` wouldn't do it: Flutter applies an autofocus only while the enclosing scope has no focused child (`_Autofocus.applyIfValid` in `focus_manager.dart`), and the page's own `Focus(autofocus: true)` (`th2_file_tabs_page.dart:1142`), or another tab's node, normally has focus (§3 change 5). The active-tab check matters because the tabs sit in an `IndexedStack`: a background tab's load can complete, and mount its body, while the user works in another tab, and the body mustn't take focus from it. The request runs only on mount, so later rebuilds don't move the focus. When the body mounts again after a Discard or an unchanged-raw leave, the controller's `_focusActiveNodeAfterFrame(canvas)` also requests the same node. The second request changes nothing. The body and the canvas are alternatives in the body `Observer` (§2), so the node is never attached twice. `dispose()` already defers disposing the node while it is attached.

**`F2`.** The page's binding already calls `toggleEditMode()`, which calls `enterTextMode()` on the canvas mode. Update its doc comment ("Broken files are left alone").

**`_enterTextModeGated`** drops `_isBroken` from its early return. For a broken file, it branches before the writer check (`:1943`), into `_enterBrokenTextModeGated()`:

1. `await _readBrokenFileSource()`. If it throws, log the error, show a localized message through `_showUserMessage`, and return: `th2BrokenFileTextInvalidEncodingMessage(basename, error.encoding)` for a `TH2SourceDecodingException` with `isKnownEncoding`, `th2BrokenFileTextUnknownEncodingMessage(basename, error.encoding)` for one without it, otherwise `th2BrokenFileTextUnreadableMessage(basename)`, for a file that can't be read anymore. Both use `p.basename(_th2File.filename)`: the full path is on the broken-file body, and a message is short. The body stays the broken-file body. After the await, it returns when the controller is disposed, the tab is closed, the mode is already `text`, or the file isn't broken anymore (a reload replaces the controller, so this only guards a stale call).
2. If `TH2TextLineEndingsAux.loneCarriageReturnOffset(source)` isn't `null`, show `th2TextUnsupportedLineEndingMessage`, as a valid file's entry does, and return (parent §4.2). The user can fix the line endings outside Mapiah and reload.
3. Skip the canvas-state steps of a valid entry: a broken file has no canvas state, selection or overlay to leave.
4. Validate the source before anything is installed. First `await beforeBrokenTextEntryValidationForTesting?.call()`, a new `@visibleForTesting static Future<void> Function()?` hook on `TH2FileEditController`, next to the other test hooks, so a test can hold the entry inside the gate. The validator's own hooks are synchronous and can't. Then `final TH2TextValidationCache cache = TH2TextValidationCache();` and `await cache.validate(source, filename: _th2File.filename, th2FileMPID: _th2File.mpID, lineEnding: _th2File.lineEnding)`. The entry already runs in the operation gate and already awaits the read, so this is one more await in the same operation. After it, the checks of step 1 run again, and the entry returns without installing anything when one fails. `validate` never throws: `TH2TextValidator.validate` turns every failure, a parser exception included, into a rejected result with an `unreadableText` diagnostic (its contract, `th2_text_validator.dart:203-204`, and its `catch`, `:350-376`), and the cache only passes that result on. So the entry adds no `try` here. An internal failure opens the session with that diagnostic marked, which the user can read, instead of a "can't read the file" message that would blame the file.
5. The cursor goes to the line of the first error diagnostic of that result that has a line (`isError && (line != null)`, in diagnostic order), at its first non-blank column. With none, it goes to line 0. It doesn't use the load's `_problems`: their line numbers describe the text the load parsed, which differs from the source when `fileBytes` isn't set and the file changed on disk after the load. The validation describes the text actually shown.
6. Install `TH2TextEditBaseline(content: source, lineMap: TH2TextLineMap.unowned(lineCount: TH2TextLineEndingsAux.lineStartOffsets(source).length), validationCache: cache, cursorLine/Column, selection, selectionRequestsFocus: true)` through `_installTextSessionOnEntry`, which sets `_editMode = text` in the same action. With `cache`, the session keeps the result, so a Save As with the buffer still unchanged doesn't parse again. The cache holds only its latest finished validation, so after an edit the result is replaced, as in any session.
7. Right after the install, `textEditController.showDiagnostics(result.diagnostics, content: source)` (existing), so the markers show with the editor, without waiting for an edit.
8. Focus `activeFocusNode` after the frame, as a valid entry does.

Entry waits for one parse of the file, about as long as the load's parse of the same text. A valid file's entry doesn't parse, so a large broken file can show a short pause between _Edit as text_ and the editor. It happens once per raw session.

The entry adds no command and no text history.

### 4.3 The raw session

A session is a **raw session** while the file is broken: `_isBroken && (_openTextSession != null)`. No other flag is needed. A raw session ends with the leave, Discard or tab close, or it is replaced after the baseline (§4.5, §4.6). So it never outlives the broken state outside the operation that clears it.

- **Line map.** `TH2TextLineMap.unowned({required int lineCount})` (new factory) builds a map with `lineCount` lines and no owners, no removed lines, no relocations and no added endings. It takes no `TH2File`: the private constructor uses its `th2File` only to extend the ranges of owned lines, so the factory passes the constructor an `ownerByLine` of `null`s and doesn't need a file. The private constructor's `th2File` parameter becomes nullable for this, asserted non-null when `ownerByLine` has an owner. `firstOwnLineOf`, `rangeOf` and `ownerOfLine` return `null` for every element. So `moveTextCursorToElement` and `copyTextFragment` do nothing, and their existing early returns cover them. The broken file's tree has no element rows, and `prepareTH2FileForTreeRead` refuses a broken controller anyway (§2).
- **Baseline docs.** `TH2TextEditBaseline`'s doc comments describe only a session on the live model: `content` is "The live model's text, as Save writes it" and `lineMap` is "The writer map of [content]". They become: `content` is the session's initial text, the live model's text as Save writes it, or in a raw session the decoded disk text of the broken file. `lineMap` is the writer map of `content`, or in a raw session an unowned map (`TH2TextLineMap.unowned`). The `initialLineMap` getter of `TH2TextEditController` and `TH2TextApplySession` gets the same note. The class comment adds that a raw session's baseline doesn't describe the model, so no code may compare it with `serializeForTextMode()` while the file is broken (§4.5).
- **Validation.** The entry validates the raw source before installing it (§4.2), and the session starts with that result in its cache and its markers shown. `TH2TextEditBaseline` gains an optional `TH2TextValidationCache? validationCache` parameter, used instead of a new cache when given. Valid entries and replacement sessions don't pass it, so they keep a new cache, as today. After that, idle validation runs on edits as for any session. Validation already parses detached with the live file's line ending and checks encodability against the detached model's encoding (Phase 2).
- **Canvas history.** `_requestCanvasHistoryGated` already refuses a broken file, so `Ctrl+Z` and `Ctrl+Shift+Z` before the first text edit do nothing in a raw session, even when the stack holds a Properties encoding change. The TH2 undo routing (Phase 3) consumes the key, so it doesn't fall through to native text undo.
- **Exclusive editing.** Phase 4's text-mode guards apply unchanged. Properties is disabled in text mode, and the tree's model-changing entry points refuse a broken controller and a controller in text mode.

### 4.4 Leaving and discarding a raw session

`_leaveTextModeGated`, after it takes the buffer lock:

- **Raw session with `session.content == session.initialContent`**: it first notes `session.sessionRevision`, then `await session.validationCache.validate(session.initialContent, filename: _th2File.filename, th2FileMPID: _th2File.mpID, lineEnding: _th2File.lineEnding)`. The validation describes the text itself, not how the buffer got there. A buffer never touched finds the entry's result (§4.2) in the cache, so nothing is parsed. A buffer edited and undone back to its initial text finds that text's result, if idle validation ran after the undo, or parses it once more. After the await, it returns when the controller is disposed, the session isn't open or its revision changed (the buffer lock keeps the content from changing). Then:
  - **Invalid**: `_returnToCanvas()` and focus after the frame, with no apply (§3 change 1). The mode becomes `canvas`, and the body `Observer` shows the broken-file body, since `isBroken` is still true. No banner shows, whatever edits came before.
  - **Valid**: the file was fixed outside Mapiah after the load (§2, _Raw text source in practice_). The path below runs, as for an edited buffer: the apply installs the baseline from the cached result without parsing again, and the canvas shows.
- **Otherwise**, and for a valid unchanged raw buffer: the existing path. `applyTextContent` handles the raw session (§4.5). On `rejected`, the banner and diagnostics are shown, and the mode stays `text`. On `applied`, the file isn't broken anymore. `_returnToCanvas()` then shows the **canvas**, and `applyTextLocation` uses `result.lineMap` (the live writer map after the baseline) and `result.cursorLine`, as for a valid file.

**The leave button's tooltip** (§3 change 12). The text view's _Canvas_ button (`TH2TextEditBodyWidget`, key `TH2TextEditBodyWidget|CanvasButton`, `th2_text_edit_body_widget.dart:62-69`) runs the leave above. In a raw session that ends in one of three ways: the canvas (the text fixes the file), the banner (edited broken text), or the broken-file body (unchanged broken text), so "Canvas (F2)" is right only in the first. Its `tooltip` becomes `th2FileEditController.isBroken ? appLocalizations.th2TextLeaveBrokenFileTooltip : appLocalizations.th2EditModeCanvasTooltip`. The toolbar actions are built inside the body's existing `Observer` (`:24`), so the tooltip follows `isBroken` with no new observer: after a Save from text mode installs the baseline, the tab stays in text mode and the tooltip turns into "Canvas (F2)", which is then true. The icon (`Icons.draw_outlined`), key and position don't change, so the button doesn't move or change shape mid-session.

`discardTextEdits()` is unchanged. In a raw session it returns to the broken-file body with the model untouched (parent §4.7, baseline step 5). The banner's _Discard text changes_ does the same.

### 4.5 The broken-file baseline in `applyTextContent`

`applyTextContent` drops its `!_isBroken` assertion (step 1 of §5) and its `unreadableText` rejection (step 2). It notes `final bool isRawSession = _isBroken` at its start. For a raw session:

1. **No unchanged shortcut.** It skips both `content == session.initialContent` checks (before the parse and after normalization). They compare against broken text that the model doesn't describe. It always validates.
2. **Validation** runs as today, including the loop that revalidates a buffer that changed during the await and the staleness checks. If the result is invalid, it returns `rejected`.
3. **Valid:** it takes the lock when `lockBufferOnAccept`, maps the cursor (`result.cursorMapper.mapRawLine(session.cursorLine)`), then calls `_installBrokenFileBaseline(result.detachedFile)` instead of the identity matcher and the command. The `serializeForTextMode() == initialContent` assertion doesn't apply. It returns `TH2TextApplyApplied(liveMap, cursorLine)` from `serializeForTextMode()`, after asserting that `liveText == result.normalizedText`.

**`_installBrokenFileBaseline(TH2File detachedFile)`** (new, `@action`, so observers see a single transition), following parent §4.7 _Broken-file baseline_:

1. `_th2File.replaceContentsFrom(TH2File.fromMap(detachedFile.toMap()))`. No image runtime cache is carried over: the detached model's MPIDs are new, so none names a live image. Images load as on a valid load. No selection, hidden set or active scrap exists to preserve.
2. `_isBroken = false`, `_problems = const <TH2FileProblem>[]` and `errorMessages.clear()`. The broken load added its parser errors to `errorMessages` (`th2_file_edit_controller.dart:703`, filled at `:898`). Nothing outside the controller reads them today, but they describe the broken model, so they go with the rest of the broken state.
3. `undoRedoController.clearUndoRedoStack()` and `updateUndoRedoStatus()`. This drops a Properties encoding change made on the broken-file body: the applied model's encoding comes from the text's `encoding` line. The clear is a stack edit that isn't guarded (Phase 4 plan, §3 change 3), and `replaceContentsFrom` isn't a command, so no mutation authorization is needed.
4. `syncControllersWithModel(initialSetup: true)`: active scrap (the first one), default snap targets, used types, selectable elements, `hasMultipleScraps`, `currentScrapName`, and the structure revision bump that rebuilds the tree with element rows. It doesn't install the reactions again: the broken load already did (`_finalFilePreparations`, §2).
5. `userInteractionController.markStationPointNameCoordinateCacheDirty()` (`th2_file_edit_user_interaction_controller.dart:195`), which marks both the Therion and the XVI station caches dirty. `syncControllersWithModel(initialSetup: true)` skips that (its step 5 runs only without `initialSetup`), since after a load the caches start dirty. Here they also start dirty today, because nothing reads them while the file is broken, but the baseline shouldn't depend on that: any later reader of a broken model would otherwise leave the fixed model with the broken model's stations.
6. `_hasUnsavedBaseline = true` and `_brokenSourceBytes = null`: the file isn't broken anymore, and its Save As collisions take the valid branches (§4.6).

**`@readonly bool _hasUnsavedBaseline = false`** (new). `enableSaveButton` becomes `!_isBroken && (_hasUndo || _hasUnsavedBaseline) && !_th2File.isNewFile`. `hasUnsavedChanges` and `canSave` follow through it. `_commitSave()` clears the flag after a successful write, for Save and Save As alike. It becomes an `@action`: the flag is observed through `enableSaveButton` and `canSave` by the dirty-mirroring reaction, and its callers, `_saveTH2FileGated` and `_saveAsTH2FileBody`, aren't actions, so a plain write would trip MobX's write policy. The action also batches the flag with `updateUndoRedoStatus()`, so `canSave` changes once. A reload clears it by replacing the controller. Undo can't reach behind the baseline: the stack is empty, and later canvas edits and text sessions stack above it as usual (parent §4.7, step 6).

The dirty-mirroring reaction watches `canSave`. In a raw session with edits, `canSave` is already true through `isDirty`, so the baseline doesn't change it, and the reaction doesn't fire twice. After a leave, `isDirty` turns false, but `enableSaveButton` is true by then, so `canSave` stays true. `t3982` records the reaction's changes of `dirtyFilePaths` with a listener.

### 4.6 Saving a raw session

- **Save.** `_saveTH2FileGated` needs no new branch. The apply runs first. A rejected apply returns `textHasProblems` and writes nothing (`t3983`). An applied one clears `_isBroken`, so the `if (_isBroken)` guard lets the write through. The session is then replaced from the live model, which turns it into an ordinary session, or the regeneration-failure exit returns to the canvas (Phase 4, §4.5), which is now the canvas and not the broken-file body. A failed write keeps the fixed model, `_hasUnsavedBaseline` and the dirty mark. The retry has nothing to apply and adds no command. Save on a broken file with no session still returns `saveFailed` and writes nothing. In a raw session with an unchanged buffer, `canSave` is false, so the UI doesn't offer Save.
- **Save As.** `_saveAsTH2FileBody` validates the buffer even when it equals `initialContent` in a raw session (§3 change 3). An invalid buffer returns `textHasProblems` with the banner shown, and no picker opens. This includes an unchanged raw buffer: the banner is deliberate there, unlike the unchanged-raw leave (§3 changes 1 and 3). After the picker, the apply installs the baseline (§4.5), and the rest of Save As runs as for a valid file: the commit clears `_hasUnsavedBaseline`, and the session is replaced. A failure before or during the write restores the filename and the image objects, as Phase 4 does, and replaces the session from the live model, which now holds the fixed text. The broken state isn't restored, since the fixed model is valid.
- **Save As target collision.** In `_handleSaveAsTargetCollision` (`th2_file_edit_controller.dart:3054`), a new first branch handles a broken other controller (§3 change 8): when the picked path didn't gain `.th2` (so the picker emptied that controller's file) and `other._brokenSourceBytes` isn't `null`, it writes those bytes back with `File(other.th2File.filename).writeAsBytesSync(bytes, flush: true)`, and a successful write counts as restored. A failed write is logged, as the valid branch's failure is, and leaves `restored` false. When the picked path gained `.th2`, the other file wasn't touched, so nothing is written, and the message is the "open in another tab" one, as today. The branch that counts another controller with `hasUnsavedChanges` as restored also requires `!other.isBroken`, so a broken controller with an edited raw session is never counted as restored without the write. So a broken other controller, with or without a raw session, edited or not, gets `th2SaveAsTargetOpenMessage` when its bytes were written back or its file wasn't touched, and `th2SaveAsTargetOpenEmptiedMessage` only when the write failed or there were no bytes. The restored bytes are those of the load: a change made to the file outside Mapiah after the load is lost, but the picker had already emptied it. Its raw session, if any, is left as it is: the user can still fix the text and save it there. Nothing is applied or renamed for this file, and nothing but the loaded bytes is written. A controller whose fix was applied but not saved isn't broken anymore, so it keeps the "already marked dirty" branch: its Save writes the fixed model.
- **Enablement.** The app bar's Save As (`th2_file_tabs_page.dart:384`) and the overflow menu's (`:696`) are enabled for a broken file while `editMode == text`, through the `Observer` that already builds them. Outside text mode, they stay disabled for a broken file.
- **Save All.** `_saveTH2ProjectFile` passes `textHasProblems` through without removing the dirty path, as for a valid file (Phase 4).

## 7. Acceptance and risks

- A broken file opens in text mode from its body, with the button or `F2`, showing the disk text with its problems marked.
- A fix applies as a new baseline: the canvas appears, set up as after a valid load, the file is unsaved, and undo can't bring back the broken model.
- Text with problems is never applied or saved. Save As with problems opens no picker.
- An unsaved fix still counts as broken for Run Therion. Reload, on the project tree's context menu until the fix is saved, brings back the broken file from disk.
- A file fixed on disk after a broken load applies with an unchanged buffer: leaving text mode shows the canvas.
- Analyzer and full test suite pass.

Risks:

1. **Raw text vs. parsed text.** The markers and the cursor come from the entry's own validation of the raw buffer (§4.2), so they are right even when the file changed on disk after the load. The broken-file body's problem list still shows the load's problems until a reload. The shared decoder (§4.1) keeps the raw buffer equal to the text a load of the same bytes parses, NUL stripping included. Saving a fixed file therefore drops the NULs, as a Save of a valid file with NULs does today. The shared decoder doesn't cover the line ending: risk 7.
2. **Unsaved fix lost on close.** Closing the tab or reloading after an unsaved fix discards it without a prompt (§4.7), as for unsaved canvas edits. The dirty dot and the Save button show it, and Phase 6's help documents it.
3. **Images after the baseline.** The baseline carries no image runtime cache (§4.5), so images referenced by the fixed text load from disk, as on a valid load. An unreadable XVI file shows its load-failure dialog once, as on a load.
4. **Picker truncation.** Save As can still empty a picked file if the write fails after the picker (Phase 4 plan, §8 risk 6). §3 change 3 only keeps the picker from opening for text that can't be applied. When the picked file is another tab's broken file, the collision restores it from its loaded bytes (§3 change 8).
5. **Original file after Save As.** A Save As of a fixed broken project file to another path renames the controller, so no loaded controller stands for the original file, which is still broken on disk. `loadedBrokenProjectTH2FilePaths()` then leaves it out, and the _Run Therion_ dialog doesn't warn about it. That matches the warning's existing scope: it only lists loaded controllers (`MPRunTherionDialogWidget`, `mp_therion_run_dialog_widget.dart:72`), so a broken project file that isn't loaded was never listed either. Reopening the original file loads it as broken, and the list has it again. Keeping a "broken on disk" path on the renamed controller, or scanning the project for broken files, is left out. Phase 6's help says so (§3 change 9).
6. **Files not valid in their encoding.** A file whose bytes its encoding can't decode (UTF-8, also used with no `encoding` line or an unknown name, ASCII, or a code page with undefined bytes), still can't be fixed inside Mapiah (§3 change 4). The invalid-encoding message names the encoding and the way out; for an unknown name, the unknown-encoding message asks for a correct `encoding` line. A rescue (UTF-8 decoded leniently, with each replaced byte marked as a blocking diagnostic until the user retypes it) is a separate issue: the validator sees only text, so it can't tell an inserted `U+FFFD` from one the file holds, and the raw session would have to carry those positions through edits.
7. **Line ending of a file changed on disk after the load.** Entry reads the source from disk again (§4.1), but the raw session validates, and the baseline is built, with `_th2File.lineEnding`, the line ending detected at the load. The detached model is seeded with it, and `TH2File.replaceContentsFrom` asserts that the two files' line endings match. So when the file's line ending changed outside Mapiah between the load and _Edit as text_ (for example, LF to CRLF), the fixed file is written with the load's line ending. Nothing is lost: the text and its lines are the same, only the line ending differs, and a reload picks up the new one. Taking the line ending from the bytes read at entry is left out: it would need a raw session's line ending that differs from the live file's, through validation, the baseline and the `replaceContentsFrom` assertion. Phase 6's help doesn't need to mention it.
